# Tiered subagent dispatch (Hermes only)

Standing preference of this user. On a delegation ask ("use kimi as a subagent", "you are the manager", /manager) the parent (default model: latest Opus) does no work and runs no commands. It writes the brief and dispatches subagents in parallel; a fresh verification subagent reruns the checks, and a blind adversarial review by the latest OpenAI sol model closes the task.

This is Hermes configuration; do not copy it into Claude Code, Codex or other harnesses (~/.claude, ~/.codex, ~/repos/skills/skill-orchestration). The manager skill carries the generic rules.

## Harness notes

- Hermes is the one harness that mixes providers. Flatiron work has no fixed parallel cap; the only limit is healthy models and disjoint file scopes.
- Skills reach a `hermes chat` child through `skills.auto_load` plus `-s <skill>`; ponytail through its plugin hook. `delegate_task` children skip `auto_load`, so their goal names each skill and says to load it with `skill_view`.

## Hermes binding for the manager

The manager runs on the default model, the latest Opus. Tiers map to models through the ladder. `intern` and `junior` usually map to the `mechanical` and `code` kinds. `principal` takes the top 3 rank values of the listed flatiron models (step 1 of the ladder). An unlisted model takes no slot.

The dependency-graph rule of the manager skill binds here:

- The scheduler is `python3 ~/.hermes/skills/manager/scripts/dag.py`. The graph file is `$TMPDIR/TASK-graph.json`, where TASK is the task name. The scheduler is dispatch machinery; the manager may run it itself.
- Flatiron children cost no quota (Harness notes). Dispatch every ready node at once and keep every ready node running.
- Put a long job in its own `delegate_task` call. Every ready node from `dag.py ready` dispatches in the same turn, one call per long node; short nodes may share one call. A batch reports only when its last child ends, so a short sibling would wait. When a finished child's report is stuck behind a sibling, a read-only subagent pulls the last assistant message from its transcript (`~/.hermes/cache/delegation/live/<deleg>/task-N.log`). The transcript's `final |` line truncates the summary to a short prefix; the full final report is normally the child's last assistant message in `~/.hermes/state.db` (`messages`, role='assistant', matched on a report phrase), read with the python3 sqlite3 module through a `file:<path>?mode=ro` URI. When a harness error cut the final turn, the stored last message is the same truncated text as the notice; salvage the child's evidence files from its scratch dir instead.
- A paid-quota child (Anthropic, OpenAI) stays at the smallest count the graph needs.
- No `delegate_task` work dispatch before `dag.py check` passes on the task graph. `dag.py show GRAPH` lists the state of each node and its unmet dependencies. `dag.py show GRAPH --slots N` adds an IDLE line when fewer nodes are ready than free slots and a node is todo. The line reads `IDLE: R ready for N free slots; split todo nodes`, printed by `show GRAPH --slots N`. Split todo nodes before dispatch. The manager skill holds the full graph rules: `path#symbol` scopes, the `Idle capacity` rule and the `without the script` fallback.

## Tiers

The manager names a tier per deliverable. The tier sets the reasoning effort, the extra skills, the fallback order and, for intern and junior, the model pin.

| Tier | Reasoning effort | Extra skills | Fallback when flatiron is down |
|------|-----------------------|--------------|--------------------------------|
| intern (usually Qwen) | low | none | Haiku, Sonnet |
| junior | high | none | Haiku, Sonnet, Opus |
| senior | high | brainstorm | Sonnet, Opus |
| principal | high | brainstorm, team, manager | Opus |

Reasoning effort tops out at high; max runs only when the user asks for it explicitly. The tier tables of this skill, `references/flatiron-routing.json` and `delegation.tiers` in config.yaml all obey it.

Each `reasoning_effort` a tier names is at most high. The router changes a value the pinned model refuses to the nearest accepted value at or above it, else to the highest accepted value. Kimi-K3 accepts `low`, `high` and `max`. Qwen accepts `xhigh`, `medium` and `low`. Mistral accepts `none` and `high`.

The reasoning effort applies only when the child runs on flatiron. The flatiron gateway serves per-model reasoning support: a tier effort a model refuses ("Unexpected reasoning effort", "Supported values are") fails the launch, and the harness still reports a normal finish. A per-model effort override lives in the `features` map of `references/flatiron-routing.json` as `effort`; `sync` writes it from the rejection text, and `pick` and `assign` clamp to it. A child that gets a refusal line in its own log reports the line and the effort it sent; the manager reroutes the deliverable. A lane-launcher brief repeats the accepted values of the models it may get (Qwen takes only xhigh, medium or low, replacing high or max with xhigh; Mistral takes only none or high, replacing low, medium or max with high) and makes the launcher NAME every value it replaced. A replaced value means the `features` map is missing that model's override: write it there after the run, or every later launch fixes the same flags by hand.

The table lives in `references/flatiron-routing.json`. `hermes-dispatch-route sync` writes it to `delegation.tiers` in config.yaml. `hermes-dispatch-route pick KIND --tier TIER` returns `hermes chat` flags; `pick` without `--tier` uses `senior`. A flatiron pick carries `--reasoning` with the effort of the tier and one `-s` per tier skill. A `delegate_task` task takes an optional `tier` field, which Hermes shows on the agents dock and applies from `delegation.tiers`.

## Standing rules

- **The manager does no work.** The manager skill states the rule; the Hermes binding adds: no routing lookups, no `hermes-dispatch-route` call, no review script, no verification rerun; every one-line check is a unit of work for a subagent. A unit with no agent mechanism is a defect to escalate, not a reason to work. Routing bootstrap: the first `delegate_task` call of a task goes to a routing subagent on the model of its tier, the tier pin or `delegation.model`. On a fresh task it returns the healthy models from the last sync (`hermes-dispatch-route models`, read-only) and the manager picks from that list for every later dispatch. A routing subagent never waits on another routing subagent. A crashed routing subagent gets a fresh dispatch, at most 2 retries on the same provider and credential setup; then it reports `blocked` with the exact error and the manager takes it to the user. A new setup (a changed key, a fixed provider, a user answer) starts a fresh retry budget. Only routing-control dispatches (`sync`, `pick`, `models`, `latest`) run before routing is fresh. (This is the Hermes binding; the manager skill's generic no-subagent fallback covers harnesses without that mechanism.)
- **Never change user settings.** Theme, skin, status line or bar, TUI widgets, display keys, `model.default` and the provider choice stay unchanged on every host, unless the user asks for that exact change. The expected change is the `delegation.*` write of `hermes-dispatch-route sync`. A brief that runs an installer, uninstaller, `unwrap` or plugin/marketplace command says: copy each config file it can touch (`~/.hermes/config.yaml`, `~/.claude/settings.json`, `~/.codex/config.toml`, opencode config) before the run, diff after, and put back every change outside the task's keys. Official uninstallers delete whole marker blocks, user entries inside included. When the user reports a theme or bar change, freeze every child that writes config in the same turn, then dispatch a read-only drift audit against the baseline and a separate restore job.
- **Process rule (every start, wait and stop).** Start long work only through `terminal(background=true, notify=true)` or `delegate_task`. Wait for its notice, or use `process_manage` actions `poll` and `wait`. Stop only with `process_manage` action `kill` or `delegate_task` action `stop`. Never kill by name with `pkill` or a `pgrep` loop: stop only processes an agent started, by PID or session id. `pgrep` is a read-only status hint only.
- **File delete and move rule.** Before an agent deletes or moves a file, check for live links to it. A live link is a symlink, hard link or config reference. If one points to the file, update the link first or keep the file.
- **Branch delete rule.** Before an agent deletes a branch (local or remote), it records the tip sha of each branch (`git rev-parse`) and the remote URL in a restore file under the task scratch dir, and the report names the file. A delete with no recorded sha cannot be undone.
- **Shared repo rule.** Never run `git stash`, `checkout`, `restore` or `reset` in a shared repo. Other agents or the user may edit there. Those commands can remove work that is still in progress.
- **Brainstorm decisions rule.** Every brief tells the child to load `brainstorm` with `skill_view`. The child uses it for each decision with more than one live option and puts the decision log in its report. The child decides alone only when the choice is reversible and inside the brief. Otherwise it returns `[ESCALATE-TO-MANAGER]` with the decision log, the options and a recommendation; it skips the user-question steps of `brainstorm`. The manager settles what it can and asks the user only what the user alone can decide.
- **Monitor cadence rule.** Hermes ends a stalled async child after 450 s idle; a child stalled in one tool ends after 1200 s (tools/async_delegation.py:86-87), and Hermes sends the result as a completion. The manager inspects on an event, never on a clock: a child's deadline passes, or the user asks. It inspects only children that have not reported back. When the harness runs more than one child at a time, the manager keeps one slot free for the inspector: a cheap read-only subagent that reads the tail of the child's live transcript and checks the liveness of the child's harness and tool processes. It reports running, not running, or unknown; unknown counts as running. Transcript silence alone never stops a child. The manager steers a running child at any time with a changed requirement. It stops a hung child when two checks in a row show no progress and liveness is not running. A brief without a deadline carries a default deadline of 60 minutes. The manager stops a child whose deadline has passed, and any child when the user cancels it or the work is unsafe.
- **Dispatch brief skills rule.** Every dispatch brief names the skills `ste`, `unslop` and `ponytail`. It tells the child to load them with `skill_view`.
- **Report first line rule.** The provider and model rule is in `../manager/references/child-rules.md`. The manager gives the `Model:` line of the `delegate_task` output header for a `delegate_task` child, and the launcher's `-flags.txt` file for a `hermes chat` task. The manager gives that line in its report to the user.
- **Child visibility rule.** In-process `delegate_task` children show live in the TUI. Ctrl+T opens the agents overlay. Pressing `t` on a row opens the child's live transcript tail. A delegate child that exits while holding background OS processes hands those processes to the parent's process roster, so they show as bare process rows without an agent row. A background `hermes chat -Q` job is invisible there. So the log-and-watch rule of step 4 stays MANDATORY in every batch status message. The manager quotes the log path and a `pgrep` watch command, as step 4 requires.
- **Removing a tool: official path first.** A read-only research subagent reads the tool's docs, `--help` and installed source, and writes the documented uninstall sequence with what each step leaves behind. The purge job runs those commands, then the installer's own uninstall (`uv tool uninstall`, `cargo uninstall`), and edits by hand only the leftovers. A tool that serves the route the subagents themselves use (a local LLM proxy) is removed last: clients switch to the direct route, a test prompt passes on it, and the service stops only when it has had no client for 2 minutes.
- **Mid-task model exclusion.** When the user excludes a model for a task ('no Kimi for now'), the exclusion covers every route to it, not only the default: `delegation.model`, the tier pins in `delegation.tiers`, and the fallback chains (`delegation.fallback_providers` and each tier's `fallback` list) in config.yaml. Before dispatching, resolve which tiers pin the excluded model and re-route this task's deliveries to the next eligible model of that tier's ladder; state the re-route in the report. Verify each completion header's Model line before relaying the result: a child can land on the excluded model through a mid-run fallback, and that work is rerun on an allowed model.
- **Flatiron first, always.** Every subagent goes to a flatiron model if any healthy one fits; Anthropic models are only the fallback of the tier. Fable is excluded unless the user explicitly allows it for a named deliverable. That permission covers only that deliverable (a UI/UX audit) and lapses with it. Dispatch it as `hermes chat --provider claude-subscription-directsdk-experimental -m fable ...`. The other deliverables of the same batch stay on the normal ladder.
- **Spread parallel work over the whole healthy flatiron set.** The user wants every up flatiron model loaded at once, for more tokens per second. Eligibility is a hard filter for `pick`, `lanes` and `assign`. A flatiron model is eligible for a kind with a `routes` list only if the list in `references/flatiron-routing.json` names it. It must be healthy and pass `--needs`. The kind `vision` takes every healthy model with `features` vision true. The `floors` key of `references/flatiron-routing.json` is the capability cut line. Code, debug, research and frontend are floored with the anchor named in `floors`. A model the ranker places in a floored kind must rank at least as high as the anchor. The kinds prose and mechanical have no floor. A missing anchor entry fails closed. A kind whose anchor is gone from the rank map fails closed too. That kind takes no new model, and `sync` logs a line that names the kind when it holds a new model back. Existing list members are never moved or removed by placement. The user's words: "if the model is too dumb for the task though it cannot be used". With no eligible healthy model, the tier fallback ladder applies. The default `pick` serves one node. All `delegate_task` children land on the configured `delegation.model`, unless their tier carries a model pin. The tiers intern and junior carry a model pin. A multi-model wave runs as `hermes chat` lane jobs. That wave uses one `assign` call with each ready node of the batch, as in the `Parallel lanes` subsection. Never split one node for show.
- **Flatiron capacity (user, 2026-10-23).** Only Qwen runs several instances on flatiron, so only Qwen takes several parallel jobs. Every other flatiron model is one instance: give it at most one job at a time, or its jobs queue behind each other. A wave status table names each job's model and elapsed time; a job queued behind a 1-capacity model reads as slowness without it and triggers a wrong escalation. Spread a wave as many cheap jobs on Qwen plus one job on each other healthy model. `delegate_task` puts every child on `delegation.model`, so a parallel wave of more than one job runs as `hermes chat` lane jobs. Qwen takes only `--reasoning` xhigh, medium or low; a launch with `high` fails before the model runs and still reads as a normal finish. A stall on a crowded one-instance model is silent: no error line lands in any log, only the elapsed time climbs while the transcript stops. On that symptom stop every lane beyond the first on that model by the process rule and re-dispatch them to other healthy models; silent queueing behind a shared instance is contention, not a model crash or an outage.
- **Web research split.** A step that needs web search or web fetch goes to `hermes-dispatch-route pick research --needs web`; the `features` map of `references/flatiron-routing.json` decides. Flatiron models never have web true. The flatiron gateway has no web search API, and the Hermes keyless search fallback does not change that. The pick returns a Claude model. That job runs fetch-only: it writes verbatim excerpts with their URLs to a scratch file and does no analysis. A flatiron child (Kimi first) then reads that file and does the analysis. Never send web search work to a flatiron child; a flatiron brief lists the URLs it needs and marks unopened facts UNVERIFIED. The UNVERIFIED mark rides into the manager's report to the user unchanged. Never relay a flatiron child's memory-based answer about an external tool's versions or bundled components as the settled finding; only the fetch-only child's quoted doc excerpt settles it.
- **Smoke tests and one-line checks in a brief run on the picked flatiron model** (`hermes chat --provider flatiron -m <picked model> -q ... -Q`), never on the default provider. `claude -p` and `codex exec` only when the check tests that tool's own config.
- **Flatiron outages are temporary.** While flatiron is down, wait at most 30 minutes for it to come back, with a cheap job pinging it every 10 minutes. Still down after 30 minutes: ask the user before any work runs on Anthropic models. Run subagents on the Anthropic fallback only after the user approves, and re-check before every new dispatch. Before each dispatch batch, a routing subagent runs `hermes-dispatch-route models --refresh`, so new or recovered models appear in `lanes`. That call checks the gateway list plus health and takes about 5 s. A full `sync` with a vision probe or the ranker can take up to about 15 minutes, so it runs in cron. Vision probes and the paid ranker stay in the 6-hourly cron. A routing subagent runs `pick` (re-probes if the last probe is > 60 s old) before each subprocess dispatch. A model that was down earlier is picked again as soon as it answers. A retry of a deliverable that failed only because flatiron was down goes back to flatiron once it is healthy; it is not an escalation. Delegation keeps the latest Haiku, Sonnet and Opus as configured fallbacks (the user's choice, in that order), so a running child can still fall back mid-run. Flag fallback work in the report. A review that ran on a fallback escalates instead of counting.
- **The model set comes from the gateway, not from a list.** A routing subagent runs `hermes-dispatch-route models`. It returns the model list with health, rank hint and the vision and web columns. `sync` probes a new model for vision with 4 quadrant questions on two random 2x2 colour grids, and the ranker ranks it. Vision true needs 4 right answers of 4; false needs 2 clear wrong answers and no inconclusive reply. A refusal that names a colour is not an answer. `sync` re-probes vision when a `features` entry is older than 7 days, or when a model has no entry. A failed, empty, truncated or refused probe answer keeps the old entry. `sync` never probes web on flatiron. When the gateway lists a new or returning model, the 6-hourly `sync` ranker places it in the `routes` lists. Placement obeys the anchor floor of that kind. Known limit: no exclusion persists while the gateway lists a model. Sync re-ranks it and placement puts it back in the `routes` lists. A hand edit of the ranks or the `routes` lists is needed only after a rejected ranker run; the sync log names the reason. A gateway model joins a routed kind only through ranker placement or a hand edit. Ranks are relative. A new model renumbers the whole set, so the ranker re-ranks the list instead of slotting one model in. The anchor floor compares the current ranks, so a renumber does not change it. A model the gateway lists no more drops out of the rank map after 7 days. The drop also removes the model from every `routes` list. After 3 rejected ranker attempts for the same unranked set, `sync` stops calling the ranker until the set changes. The ranker-rejects state, the lock and the dated backups live in `~/.hermes/cache/dispatch-route/`. Then hand-rank, from the reason in the sync log. Each ranker run costs paid quota.
- **Fast mode once the work is small.** For a final fix round (docs, test helpers, a few lines), cut it into parallel deliverables in one `delegate_task` batch and spend builds only where a change needs them. Doc/comment-only deliverables get no build at all (the brief says "do not run cmake"). Code or test changes rebuild only their own targets, incrementally, in an existing configured build dir (`cmake --build . -j8 --target <t1> <t2>`), then run each rebuilt binary IN FULL (no tag filter; a full test binary costs seconds). No full suite, sanitizer or benchmark build unless the change touches shared library code. The report names what was not run and why.
- **Builds run at the lowest priority.** Every brief that builds, compiles or runs a test suite says: run it with `nice -n 19 ionice -c 3 <cmd>` (macOS: `nice -n 19`). Launch the `hermes chat` child itself under `nice -n 19` too; the priority is inherited by everything it spawns. When the rule arrives while children already run, a control subagent renices them in place (`renice -n 19 -p <pid>`, `ionice -c 3 -p <pid>` on each child PID and its descendants) and the children keep running. Priority changes never stop or restart work. The global agent rule files in ~/dotfiles carry the same rule.
- **Cheapest able model, then parallel.** Simple work goes to the cheapest able model in a `hermes chat` lane job. Simple work is the tiers intern and junior, and the kinds mechanical and prose. The cheapest model is the model with the lowest rank value in `references/flatiron-routing.json`. Mechanical and intern work goes to the fastest model that passes, usually Qwen. A tier with `prefer: cheapest` has this in the json. In a `hermes chat` lane, `pick` and `assign` choose per kind and tier. `pick KIND --tier TIER` returns the cheapest healthy model in the `routes` list of KIND, not for the mechanical kind and the intern tier. So `pick prose --tier junior` returns the cheapest healthy model in `routes.prose`. A `delegate_task` child cannot choose a model per kind. For each cheap tier, `sync` pins one model from one lane. Sync pins the intern tier to the first lane for the mechanical kind, with no capacity check. `pick` checks capacity at each dispatch. The principal tier keeps its anchor-first pick. Qwen-first does not apply to it. The junior pin is the cheapest healthy model in `routes.code`. A junior `delegate_task` child on prose or mechanical work runs on the code pin. Send cheap prose and mechanical work as a `hermes chat` lane job with `pick KIND --tier junior`. When no model in the lane is healthy, `sync` drops that tier pin, and the child uses `delegation.model`. `assign` spreads parallel nodes over all eligible models by in-flight load. The tiers senior and principal keep the strength floors.
- **Cheap first, escalate on failure.** Start every work deliverable at the cheapest tier that can plausibly do it, usually intern or junior. Each manager splits work until each leaf fits that tier, then starts the leaf there. A child that can spawn does the same for its own leaf nodes. A failed check, a crash or no progress reruns the deliverable one tier up with `pick --failed`. Before the rerun, the manager runs `dag.py fail GRAPH ID`, then `dag.py escalate GRAPH ID`. That command moves the tier one step up. A `principal` leaf that does not succeed goes to the parent manager. A harness-ended "Response Stopped - Repetition Detected" stall (exit 1, the partial response discarded, the session id on the log's last line) is a crash of the author, not a verdict: salvage the leftover with `git -C <wt> diff > <scratch>/<job>-leftover.diff`, route the rescue to the next `pick --failed` rung, and apply the manager skill's rescue-keep gate before reusing any of the diff. Edits that restructure a shared function across whole regions stall the cheapest models into those loops; route that class one tier up from the start, even when every single change inside it is small. Never start at senior or principal only because the task looks big. Reviews start one tier above the author's tier, because a missed defect by a weak reviewer reads as a pass and nothing triggers an escalation. A cheap-tier pin model caught fabricating a success report starts each subsequent report-bearing deliverable of that task one tier up. The manager records a `fabricated` verdict in the outcome ledger. Verify-before-accept catches the fake either way, but re-routing through the same pin wastes a full round.
- **Issue sweeps split per issue, not per repo.** A "fix the open issues in these repos" ask starts with one read-only discovery child listing open issues and PRs per repo; only repos with open work get nodes. Each fixable issue is its own junior-tier `hermes chat` lane in its own worktree, the brief quoting the issue body verbatim and ending with one mutation-check test. Bundling several issues into one repo lane serializes fast independent fixes and invites the output-loop stall above. The user's reported wrong-result lines (asm the hover mis-handles) sweep the same way: first the cause-triage child reads each line against the code, then one fix child per independent cause.
- **Split fix rounds.** A fix round with more than one finding runs one child for each function or each file. Each child has its own worktree. The round adds one merge node. Findings that edit the same function stay in one child. Text-only and doc-only parts go to the cheapest able model and run no tests. The real-agent check and the re-review run in parallel after the merge. One serial child with five fixes and three mutation checks took more than an hour. Rules every lane of a wave shares (worktree rules, compiler pin, stop rules, report contract) go in one common preamble file; each lane's launch brief is the concatenation of its per-slice file and the common file, built in the launch turn. A mid-wave rule change then lands in one file, and two briefs can never drift apart on a rule the manager edited in only one.

## Ladder (per deliverable)

1. **Best eligible flatiron model for the task kind.** A routing subagent runs `hermes-dispatch-route pick <kind> [--tier <tier>]`. The kinds are code, debug, frontend, research, prose, mechanical and vision. It returns the result. It probes the gateway (60 s cache; `--refresh` forces) and returns `{provider, model, flags, reason, skipped}`. Ranks and per-kind preferences live in `references/flatiron-routing.json`, which holds the live rank order. A `principal` tier takes only the 3 highest rank values of the listed models here, since ranks are relative. For the `principal` tier the pick leads with the kind's `floors` anchor, the escalation model, whatever the `routes` order says.
2. **It fails** (bad result after one corrective follow-up, crash, no progress): a routing subagent reruns `pick` with `--failed <every model that failed so far>`. It returns a flatiron model STRICTLY STRONGER than every failed one if one is healthy, else the first rung of the tier's fallback list: the latest Haiku (`hermes-dispatch-route latest haiku`) for `intern` and `junior`, the latest Sonnet for `senior`, the latest Opus for `principal`.
3. **A fallback rung fails:** a routing subagent reruns the same `pick` call and it returns the next rung of the list (Haiku, then Sonnet, then Opus). When the list is used up, `pick` returns `provider: null`: stop and take it to the user.

Escalate only the failing deliverables, not the whole task. One exception is task-wide: after a cheap-tier pin model caught fabricating a success report, subsequent report-bearing deliverables of that task start one tier up. Other models and non-report work keep cheapest-first. Resolve "latest" live from the Claude account picker and Hermes' codex catalog (`hermes-dispatch-route latest opus|sonnet|sol|haiku`, 24 h cache); never hardcode ids in briefs.

The kind `vision` is for screenshot verdicts and reports. The `features` map of `references/flatiron-routing.json` decides: `pick vision` (same as `--needs vision`) keeps only models with vision true. The latest Haiku is the fallback only when no flatiron model has vision true. When Haiku reports unsure, a routing subagent reruns `pick vision --failed <Haiku id>` and gets the latest Sonnet. For the `principal` tier, `vision` never returns Haiku; it follows the tier list (Opus).

In-process `delegate_task` children use `delegation.provider/model` in config.yaml, unless their tier carries a model pin. `hermes-dispatch-route sync` sets it to the highest-ranked healthy flatiron model. When none is healthy, sync keeps the flatiron Kimi-K3 default, and the `delegation.fallback_providers` chain takes over: latest Haiku, then latest Sonnet, then latest Opus. `hermes-dispatch-route sync` writes only the `delegation.*` keys from live discovery (also cron every 6 h, log `~/.hermes/logs/dispatch-route-sync.log`); it does not change `model.default`. Never hand-set a literal id. Resolve the reviewer's sol id live per run. Discovery failure is a hard error, never a silent literal fallback. For any other pick (GLM, Mistral, a later rung) use the subprocess form of step 3, because delegate_task cannot choose a model per task. A rung equal to a tier pin may run as a `delegate_task` child of that tier. A mid-session model request of the user ('use Kimi too') changes only new dispatches; in-flight `delegate_task` children keep their tier model, so do not restart them. `hermes-dispatch-route latest` resolves only the four Anthropic/OpenAI families (opus, sonnet, sol, haiku); a flatiron id comes from `hermes-dispatch-route models`, and the child launches as a pinned one-shot: `hermes chat --provider flatiron -m <id> -Q --query-file <brief>` with the tier's reasoning and `-s` skills.

### Parallel lanes

Before each batch, a routing subagent runs `hermes-dispatch-route assign NODE=KIND:TIER[:NEED,NEED] ...` with each ready node of the batch. The command prints one JSON entry for each node. Each entry has node, kind, tier, provider, model, flags, load, reason and fallback. Each node goes to the eligible model with the fewest in-flight jobs, and ties break by pick order. The count increases by 1 for each assignment in the batch. Each model has a cap: the `capacity` map in `references/flatiron-routing.json`, default 1. `assign` skips a model whose in-flight count plus this batch's assignments reached its cap. When every eligible model is full, the node goes to the model with the most capacity left (negative counts kept), never to the fallback ladder. The in-flight count is a live scan of `hermes chat --provider flatiron` processes. The scan matches the model argument in the forms `-m MODEL`, `--model MODEL` and `--model=MODEL`. There is no state file, so the count cannot go stale. Each node launches as `hermes chat <flags>` per step 3. A vision node runs with `--needs vision`. The standing rules hold the eligibility rule and the user's words. The command re-reads health each batch. No eligible model fits: one entry with `"fallback": true`, the rung `pick` would return.

### Outcome ledger (model-strength learning)

The manager alone appends one row to `~/.hermes/cache/dispatch-route/outcomes.jsonl` for each child outcome. The leaf child does not write the ledger. Each JSONL row has the fields `ts`, `node`, `kind`, `tier`, `model`, `verdict` and `note`. The verdict is `pass`, `interrupted` or `blocked`, or one of `hung`, `fabricated`, `missed-defects`, or a verdict that starts with `failed`. An `interrupted` or `blocked` verdict is not a `failed` verdict.

Before each dispatch batch, the routing child runs `tail -200` on the ledger. It adds a leaders-per-kind summary to each new brief: model, observed pass rate on that kind, n. A pattern with at least 5 consistent outcomes goes into the model-notes block at the next review round. `pick`, `lanes` and `assign` skip a model for a kind when its last 3 ledger rows for that kind all have a bad verdict. A bad verdict is `hung`, `fabricated`, `missed-defects`, or a verdict that starts with `failed`. A hyphenated verdict counts as its stem. Mechanical and intern picks prefer the Qwen lane.

When a brief pins a tier or model, the ledger row records the landed model from the completion `Model:` line (report first line rule). A fallback landing is flagged, not rerun (the flag rule of `Flatiron outages are temporary`).

The ledger is per-host cache. Never commit it. Rotate it at 10k rows.

## Procedure

0. **Before any edit**, a subagent records the baseline for the review and returns only the value the manager needs:
   - git repo: the subagent runs `git -C <repo> rev-parse HEAD` and reports the sha as BASE (commits made later by children are still inside BASE..worktree).
   - files outside git (config, dotfiles, skills): the subagent runs `hermes-adversarial-review --snapshot-create <task> <path>...` (paths may not exist yet) and reports the snapshot path. When the scope grows mid-task, a subagent snapshots the new path BEFORE the work dispatch; otherwise sol never sees it (often the riskiest part: auth, credentials). Both baselines come before the first config-writing routing `sync`, so the review diff holds the state the task started from.
0c. **Selftest baseline before the first routing edit.** Before a brief edits `references/flatiron-routing.json`, the router or skill tier tables, run `python3 scripts/selftest.py` on the UNEDITED files and record the result. A brief whose stop rule treats any selftest failure as caused by its own edit reverts good work when the failure predates it: with a baseline on file, a failing edited run that matches the baseline is a pre-existing failure to report, never a reason to revert. `selftest.py` stops at the first failed assert, so the checks after the failing one never run; when the baseline is red, gate the edit with the per-check runner of `references/routing-selftest-gates.md`, which must show IDENTICAL PASS/FAIL lines for the unedited and edited json. An edited json whose per-check line flips a PASS to FAIL reverts.
0d. **A three-way doc disagreement goes to the user, not to a source pick.** `references/flatiron-routing.json`, the router script docstring and `selftest.py` are three separate files and can state three different behaviours for one tier. When they disagree on behaviour (not on wording), never resolve the mismatch by picking the source that looks newest; a docstring and json that were edited together signal a deliberate change, never assume it was an accident. Report the exact file:line of each source and ask the user which behaviour is intended; then fix every stating source to match the decision.
0e. **Reverse-toggle evidence for a routing behaviour claim.** A claim "field X drives pick result Y" is reported with both directions: run `pick` in-process on a scratch copy with the field as-is and once with the alternative value, and quote both outputs. One direction alone cannot separate "the file is wrong" from "the test or router code is wrong", and a fix then lands on the wrong file. Scratch copies only; never toggle the live json.
0b. **Skill preflight.** For each deliverable, name the skills the work needs: the standing writing skills `ste`, `unslop`, the ponytail mode, plus task skills. Before the work goes out, make sure the harness of the child has each skill installed (missing skill: a first cheap work batch installs it from its source, then the work batch starts). The child gets the skills through the mechanism of that harness (`-s <skill>` for `hermes chat`; other harnesses: `references/harness-skill-delivery.md`). The brief names them.
   - User rule, owned skills (`github.com/DiamonDinoia/skill-*`): install from the marketplace of each harness. An agent or the curator may edit an installed copy of a skill. Each edit must pass review and go upstream into the clone on a branch before the next release. Review before release, version bump in every manifest, machine-specific text stays out of the public repo. Release scanner, rollout checks, worktree and prototype rules: `references/harness-audit-workflow.md` (section: owned skills).
   - Edit rule, owned skills: an agent or the curator may edit an installed copy of a skill. Each edit must pass review and go upstream into the clone on a branch before the next release. A release first carries every installed-only edit: diff the installed copy against the last released commit; the curator edit log lists the edits. The curator can patch the same installed copy while an edit job runs; quote each old line and re-read it right before patching, or the patch anchors to a stale read and clobbers the curator's line.
1. Dispatch an intern subagent that does the routing research (paths, existing pieces to reuse) and reports only what the briefs need. The manager does not implement: send one-line `config.yaml` edits, wrapper scripts and widget tweaks as a deliverable, or bundle them into a running child's brief. Read-only work such as "review PR N" is the same: a subagent fetches the PR metadata and `--stat`, then the manager dispatches the review as deliverables (build and run what the PR changes at both merge base and head, test each questionable value against alternatives, static checks for the rest). The manager does not read the diff. A read-only task produces no diff, so step 7 does not apply; say so in the report. Step 5 still applies: a fresh subagent reruns the child's decisive repro, and pushes past a cause it leaves as "needs investigation". The real root cause is usually one level below where the child stopped.

It holds the goal, the files in scope, the pieces to use, and the rules (prefer config/plugin files to source patches). It holds a concrete CHECK for each deliverable that catches a defect. It holds one line that names `../manager/references/child-rules.md`, the rule that a `diff` travels as `--stat` only, and `[ESCALATE-TO-MANAGER]` for items the child cannot do. Keep briefs out of the repo. The reviewer must not see them. The manager sends the brief content to the subagent. The subagent writes the file and gives the path.
3. A launcher subagent dispatches the work as a background Hermes process with the picked flags:

   via `terminal(background=true, notify=true)`. The launcher writes the picked flags to `<job>-flags.txt` in the same command (`echo "$S" > <job>-flags.txt`), so the model of every job stays knowable. The launcher subagent stays alive until the notice of the child arrives, then returns the log path, the session id and the final report. A launcher that returns while its background work still runs orphans that work: the harness tears down a session's background processes with the session. A job no launcher can wait out is started by the parent itself with `terminal(background=true, notify=true)`. One such job is a sweep longer than any reasonable launcher lifetime. It runs under a tracked supervisor. The supervisor is a background process with a session id, a completion notice and a named owner who can stop it. `-Q` prints only the final answer + a `session_id:` line; an empty log mid-run is normal, watch mtimes of in-scope files.

It arms `terminal(background=true, notify=true)` and ends the turn, or it calls `process_manage` action `wait` on the session id of each watched worker and repeats the call until the process exits: each call is an event wait clamped to TERMINAL_TIMEOUT (default 180 s) and a timeout result never kills the process. Fixed intervals and `heartbeat=` scripts are forbidden as wait mechanisms. A name-based `pgrep -f` is a read-only status hint only and never decides that work is done. The monitor relays a short status when an event arrives; when the user sets a cadence such as "wait 30 mins between checks", it reports at that cadence instead. The monitor stays alive until the watched work ends and reports the last status line before it exits, because a background script started by a child that has already exited delivers no notification to the manager. A `-Q` background child is invisible in the TUI, so the same message gives the user the watch commands: `pgrep -af <brief-name>` (alive?), `git -C <repo> status` (edits landing) and the log path (final report). If the user says they don't see it working, a subagent first checks the child is still alive; it may have exited early, and the log's last message lists what's left. Resume that session with only the remaining deliverables.

When `git diff` shows the child's edits complete and it has spent a long time on local verification only, stop it, review the diff, run one quick local check (native build + the targeted tests), fold the edits in (fixup + autosquash), run the CI-version style checks, and push the feature branch. The PR's CI matrix is the validation, and the monitor relays the CI counts when a CI event arrives (a check finishes or `gh run watch --exit-status` returns), not on a clock. Say in the report which local checks were skipped.

Run `pgrep -af '[h]ermes chat'` before you report or wait on it; for the wait itself, use the process rule, never the name pattern. If it is gone and its log has no report, dispatch the deliverable again with a fresh brief and say so to the user.
5. On completion: a fresh verification subagent that did not write the code reads the log's final report, does `git diff` in the source tree, reads the changed files, runs the checks (for UI work: tmux capture/screenshot), and reports the verdict. Subagent self-reports routinely claim success on deliverables that are wrong.
5b. **Probe.** The probe checks the real worker, not a separate process. The worker's first reply must quote each skill it was given: the standing skills (`ste`, `unslop`, ponytail) plus the task skills named in the brief. Accept only a quote that really sits in the skill file. A missing or wrong quote means the worker did not get the skill. Do the preflight of step 0b again. For layout claims ("column fixed", "never shifts", "fits"), the verification subagent measures the column indices in the child's verbatim captured lines before the manager accepts. The captures can contradict the claim on their face, and the vision verdict on a PNG checks order, not alignment.
6. Follow-ups: resume the same subagent session so it keeps context: add `--resume <session_id>` (from the log's last line) with a new `--query-file` listing only the failed deliverables and their checks. The session id is also in `~/.hermes/state.db` (`select id, model, title from sessions order by started_at desc`).
6b. **The user changes the spec mid-run** (common): write the change as a numbered `SPEC CHANGE` brief that says what it overrides. Stop the child by the process rule. Cat the earlier briefs plus the change into one file and resume the same session with it. Never kill by name: the pattern can match a sibling agent on the same repo or brief prefix. After the stop, keep only the child's own changes. Use its commits, or a patch of only its files: `git diff BASE -- <paths>`, plus staged and untracked files it added. Never restore or check out files the child did not change. Confirm the stop with `process_manage` poll. Relaunching without the earlier briefs drops their deliverables. The killed run's exit-130 notification arrives later; say it was the stopped run and do nothing else. A resource change mid-run (a wider core mask, a bigger RAM cap, a faster host lane) is a spec change of the same shape, but the cap lives in two places: the launch line (taskset range, systemd-run scope) and the brief's own parallelism numbers (build -j, sweep -P). Retasking the live process widens only the OS mask and leaves the agent's old parallelism caps in force, so stop the job and resume the session under a new launch scope with a numbered spec-change doc that rewrites both the caps and the parallelism numbers. For in-process `delegate_task` children, don't kill: patch the spec file first, then `delegate_task(action='steer', subagent_id, message)` with the delta and its check (tell sibling children too if their scope is affected). ## Parallel fix rounds by subsystem

A FAIL with findings in several independent subsystems of one branch fixes faster in parallel. Cut the findings by subsystem (each group whose fixes touch disjoint files), one fix child per group, each in its own worktree on a new branch from the FAILED head, never from a sibling's branch. Each brief carries: its findings verbatim, an exclusive file-ownership list, the sibling-owned files it must not touch, and the rule that a finding fixable only in a sibling's file returns [ESCALATE-TO-MANAGER] instead of editing across the line. Each child verifies its sha at step 0 against the failed head. A single-owner resource stays single-owner across the round (one Playwright port, one device): every brief names its one owner; the other children run their checks without it. When one fix adds an API another fix should consume (a new keyword the sibling-owned file should pass), neither child crosses the ownership line to wire it; the merge node wires it after both sides land. A fix that cannot finish without the wiring escalates instead of editing across the line. Merge the fix branches into the integration branch in one merge node; a conflict the merge hits is a defect in the ownership cut, fix the merge itself, then rerun the merged tree's suites. The merge node proves the union before the suites run, so a silently dropped fix branch never reaches review: the diff of the pre-fix stack tip against the merged tip, restricted to the union of the fix paths, must equal the combined fix diffs, and the report carries the mismatch count, which must be 0. The merge brief pre-declares the expected value of every check it runs (suite counts, per-probe wrong counts) from the fix reports, before the runs start; the merge report prints one expected-vs-observed row per check. Values declared after observing let the integrator copy its own output as the verdict. Re-review the merged head as a fresh blind run against the same BASE; the re-review brief still enumerates the original goal findings, and the gate is those plus regressions from the fix round.
   Findings handling, fix rounds, push gates, stop conditions: `references/review-loop-rules.md`. Load it before the first review run; first-review needs (combined review, isolation handling) live there.
7b. **User rule: after a PASS, PR per repo, then merge when CI is green.** Push the branch, `gh pr create`, and launch `scripts/merge-when-green.py <owner/repo> <pr>` as `terminal(background=true, notify=true)`. It squash-merges once every `pull_request` run on the head SHA passed, reruns a cancelled run's failed jobs once (`gh run rerun <id> --failed`; a runner cancel is not a code failure), and stops without merging on a real failure; then triage the first error. Repos that PASS go out at once; a repo still in a fix round does not hold them back. Don't read `gh pr checks` fail counts as CI failures: the push-event runs on the same SHA show as cancelled/fail once the PR runs start. Compare against `gh run list -b main` before telling the user anything broke. Hosted-runner incidents: `references/git-ci-pitfalls.md`. CI maintenance (version bumps, runner pinning, publishing auth, releases): `references/ci-maintenance.md`.

## Pitfalls

- After editing either script, run `python3 scripts/selftest.py` (offline: ladder order, outage/recovery, monotonic escalation, isolation checks, snapshot excludes, exit codes).

- Flatiron models go down individually (vLLM host "Cannot connect", 500s or timeouts) and come back later. `pick`/`sync` skip unhealthy ones. A model dying mid-run is an outage, not a quality failure: redo the deliverable on the next pick without adding it to `--failed`, unless it produced a bad result.

- A 401 from `curl 127.0.0.1:8788/v1/models` without a key is expected; the flatiron provider reads `FLATIRON_GW_API_KEY` from env/.env. But when `pick` itself lists every flatiron model as `HTTP Error 401: Unauthorized`, that's an auth problem (key expired/missing in env), not an outage: fall back along the fallback list of the tier (see Tiers) and tell the user the gateway key may need refreshing.

- Numeric heuristic fits (tolerances, error floors, warn/refuse constants): `references/numeric-heuristics.md`. Load before dispatching a child that tunes a bound on a numerical library.

- The 6-hourly `sync` cron races live router or json edits. It rewrites the json with whatever router is installed at that moment. On a half-installed change it can spend a paid ranker run. Before the edit, read the tail of `~/.hermes/logs/dispatch-route-sync.log` and snapshot the json; after the install, diff the live json against the expected state. An unexplained json change near the top of a 6 h block is a cron sync, not the edit job.

A model marked vision:false in the routing features list may still accept video through the chat API (the flatiron MiMo model does). Classify that from the provider and model docs, not the features map. Use MiMo on video only with a control pair, a static clip and a deliberately broken clip. It reported a moving video as static. It also missed an artificial loop join. Never trust its loop-seam or motion verdicts alone. Its domain: reviewer models that read media.
- A capability probe for vision, web or audio, whose prompt is answerable from training memory, is no probe. The model answers without calling the tool. The probe then reports a capability the provider lacks. Probe with input only the live tool can return. Use an image generated on the spot, or a page published after the training cutoff. Re-run the evidence command before relaying the claim.

- A user style decision on an idiom (a multiline ternary, a name) is binding. Reach the worker with `delegate_task(action='steer')` before it folds the change.

- A README line that quotes a performance number or the formula behind a probability comment must be reproducible by whoever reads it. The reviewer who cannot rerun it reads it as a shipped claim and fails it. Write the rule in prose ("cold runs grow with the number of near-duplicate chunks"), keep every quoted number tied to a committed generator or the exact command that produced it, and spell out the inputs behind a comment that states a computed probability.

- A one-shot `hermes chat -Q` launcher has a child budget of 2, `delegation.oneshot_max_children`, and it delegates synchronously. A review that needs more fresh reviewers runs each as a separate `hermes chat` job the parent launches. An inline review in the launcher does not count as the internal review. A review job that finds it cannot spawn sub-reviewers (the one-shot budget is spent) reviews inline in its own fresh session and says so; the manager relays that fan-out waiver in its report, so the user can weigh a verdict that rests on one blind session.

- A `delegate_task` child pinned to a 1-capacity flatiron model takes most of an hour on a fix bundle with several findings, edits and a test suite; observed runs land near the 60-minute default deadline. Give such a brief 75-90 minutes, keep the commit-as-soon-as-its-check-passes rule so a deadline cut loses at most one deliverable, and spread a wave over several flatiron models instead of queueing on one.

- Size every `delegate_task` batch to the free background slots (`delegation.max_concurrent_children` minus in-flight children): overflow tasks do not queue, they run SYNCHRONOUSLY in the parent turn, so the parent model stays awake and burns paid quota for the whole child duration while showing an ordinary 'assumes' report. When more nodes are ready than slots, dispatch only what fits, close the batch call, end the turn, and dispatch the rest when the completion notices arrive. The user watches the paid quota; a manager turn blocked on a synchronous child is the same cost as the manager doing the work itself. Budget by message, not by call: tasks dispatched earlier in the same assistant message already hold slots when the next delegate_task call launches, so a wave split across several calls sizes each later call by free slots minus the tasks this message already dispatched.

- A child that leaves its venv runs tests with the system python and every test fails on `ModuleNotFoundError`. Name the exact interpreter in the brief (`<venv>/bin/python -m pytest`), and when a child reports a mass import failure, steer it to rerun with that interpreter before treating it as a code failure. For the Hermes repo's own tests the interpreter is the newest match of `~/.hermes/installs/*/test-environment/gen-*/venv/bin/python`; resolve the glob before dispatch, several installs can match.

- Long fix rounds get interrupted (provider errors, dropped model connections). Put in every brief: "commit each deliverable as soon as its CHECK passes", so an interruption loses at most one deliverable and the next run can start from `git log`.

- On the laptop `grep` resolves to rg, so a briefed `grep -E <pat>` dies on the flag parse. Briefs for that host use rg syntax or `/usr/bin/grep`.

- A child can run its commands in the wrong worktree or repo (one stopped at its own STEP 0 because its `git log` ran in a sibling repo's worktree and showed that repo's tip). For sibling worktrees give absolute paths in the brief and require `git -C <worktree>` for every git command, never a bare `cd` the harness can lose.

- Parallel children on one task: name the file OWNER in every brief ("X belongs to another agent; do not edit it, only check it"). Two children otherwise edit the same widget/config at once and clobber each other.

- A brief's stop rule must match the observed state, not a remembered one: this box's dotfiles seeds `~/.hermes/config.yaml` as a REGULAR file (setup.sh copies it once from `seeds/hermes/config.yaml`), so a 'must be a symlink' stop rule is wrong and costs a whole child run. Verify stop rules against the current tree before dispatch; check `BOOTSTRAP.md` and `setup.sh` for the intended shape of per-host files.

- An interrupted turn kills its in-flight `delegate_task` children with it (`status=interrupted`, partial work in scratch). Take over with a FRESH child whose FIRST step is read-only state discovery (git HEADs, file existence, mtimes), then act only on what is missing; never trust a partial output row as progress.

- Put in every brief: "do not create or edit skills or memory". Children otherwise create skills on their own, which clutters the library and can leak into the thing being built.

- A recommendation question the user leaves unanswered while work is ready does not block. Proceed on the recommended option, keep the other option reachable (a `backup/<name>` branch at the verified alternative, with its check result), and say both in the report so the user can switch with one word. Never push on an unanswered question that is outward-facing; prepare both and wait.

- When two candidate fixes are measured against each other and one already meets the contract, the other stays unbuilt. The brief says "pick the first variant whose sweep is clean", not "measure both". A full V2 run on a large grid when V1 already gives 0 misses costs a child its deadline and turns an answer into a comparison table the user never asked for. Report the pick, the winning variant's sweep, and one line of why the other was skipped.

- A build or test suite whose inputs are proven byte-identical to an earlier passing run is not re-run. Inputs are the final tree, the configure flags and the toolchain, not the patch alone. Prove each part: `cmp` of the two patches, an empty `git diff <old> <new>` of the final trees, a diff of the configure command or `CMakeCache.txt`, and the same resolved compiler (`readlink -f $(command -v cc)`) with equal `sha256sum` of that binary; report that evidence, not a rerun.

- Spec questions go in one batched `clarify` call with a recommended option per question. Dispatch changes only after the answer. Any proposal the questions refer to (an animation table, a design list) must already be on screen in an assistant message BEFORE the `clarify` call, or written into the question text. An interrupted turn loses the drafted text, and the user then approves something they never saw. If that happens, show the proposal in the next report and invite overrides.

- A subagent regenerates a child's patch from its worktree (`git -C <wt> diff <base> > $TMPDIR/x.patch`) before applying it. Children write the patch file mid-run and then keep editing, so the file they name can be stale or carry a hunk they already reverted.

A report that leads with `Runtime:` or `Provider:` names the launcher of the runtime block only as decoration: the proof the intended model served the work is the child's OWN first line, the completion `Model:`/session row, or the state.db session row. A `Provider: custom` line on a Kimi-K3 run launched with `--provider flatiron -m moonshotai/Kimi-K3` is correct, not a reason to rerun: the custom label is how Hermes binds a third-party gateway for that model. The manager checks `~/.hermes/state.db` (`messages`, role='assistant', matched on report phrases, `file:<path>?mode=ro` through the python3 sqlite3 module) when the summary prefix is absent, before re-dispatching.

- Git history rewrites (fixup+autosquash, amend, force-push, branch moves): `references/git-history-rewrite.md`. The autosquash base is the pushed PR head; only a fix on a commit below it (upstream code) goes in a new commit on top.

- A routing ship's gate runs a live `pick <kind> --tier <tier>` for every affected tier and asserts the exact model and flags verbatim. Exit 0 alone passes on a reordered routes list that serves a wrong model. Route order is placement data, not a tier pin. A later `sync` re-sorts by strength, so a tier invariant such as "the anchor holds the principal pick" lives in the pick logic, never in list order alone. Restoring a list order to recover a pick regresses at the next sync.
- A `steer` delivered mid-run queues on the child's next tool result; a literal `sleep` loop in the child blocks that delivery until it wakes, so a single `steer` does not reach a sleep-polling child, and the child keeps its plan while the manager thinks the plan changed. Never leave a child in a sleep poll: steer it to wait on the event mechanism (process_manage wait, a notify slot) instead, or stop and redispatch with a bounded nondeterministic wait. A `pgrep -af` the manager runs is a read-only liveness hint only, never a wait reason.
