# UI redesign asks: options to pick, not one proposal

Load for UI redesign or simplification asks, and for UI work built from the user's picks.

**User rule for UI redesign/simplification asks: options to pick, not one proposal.** Two deliverables in order, chained in one background command (`<design job>; test -s <proposal.md> && <mock job>`), since the second job reads the first one's output. (1) The design job (Fable when the user allows it, else the ladder) screenshots similar reference UIs into `refs/`, then writes `proposal.md` as AREAS (filters, result list, detail, landing, mobile, TUI). Each area gets 2-3 options with ids (`A1`, `A2`), plus "keep as is". Each option names the reference it borrows from, the files it touches, its diff size, and a MOCK SPEC another engineer can build without questions. It also lists options that conflict across areas. It builds nothing. (2) A Kimi job builds one live mock directory per option: a copy of the real web files with only that option applied, all on the shared real data, so search works. It also builds a gallery `index.html` with a radio button per area and a "Copy my picks" button that outputs `A2 B1 C-keep`. Checks: Playwright loads each mock, runs a real query, sees zero console errors and a screenshot that differs from base, and every option id in proposal.md appears in the gallery. The user picks in the browser and pastes the string back; implementation briefs come from those picks. The mock brief orders the work so something usable lands early: first `base/` plus the gallery `index.html`, then ONE mock per area (the proposal's recommended option), then the Playwright check and a report, and only then the remaining options. It says "read only what each mock needs; write the first file within your first few steps". A mock child that has written no file under its output dir after ~15 min is a failed run (it is reading the whole CSS/JS tree). Stop it and do not resume that session, because a resumed session keeps reading. Start a FRESH Kimi session first with a concrete brief: the state already on disk, the exact files to write, one builder function per option id, and the checks. Escalate with `pick frontend --failed <model>` only after that fresh Kimi run also fails. When a higher rung did part of the work, hand the rest back to Kimi with a state-listing brief. The user asks "why Sonnet instead of Kimi" otherwise, so name the model and the reason in the report whenever a job leaves Kimi. **User rule: the gallery shows what each option looks like and why.** Every option card (keep-as-is included) carries the mock screenshot (click opens it full size), a link to the live mock, 2-4 sentences of rationale from proposal.md (what changes, the problem it fixes, the reference it copies, diff size) and a thumbnail of that reference screenshot. TUI options get the proposal text plus the current TUI screenshot. `gen_gallery.py` generates the cards from proposal.md, so new options need no hand edits. The gallery CHECK asserts: a card per option id, every `<img>` has `naturalWidth > 0` (force eager loading and scroll first, lazy images report 0), every rationale >= 80 chars, the picks string, zero console errors. Serve the result with `exec python3 -m http.server 8765 --bind 127.0.0.1` from the gallery dir as a background terminal, and give the user the URL plus the `ssh -L` line. The server can stop answering after hours while it still listens (`ERR_EMPTY_RESPONSE`): before every report that names the URL, run `curl -s -m 5 -o /dev/null -w '%{http_code}'` on it, and on anything but 200 stop the server by the process rule and start it again. Both jobs work only in scratch and leave the repos untouched. The design job also lists plain bugs (dead filters, wrong counts, overflow, key handling) apart from the taste options, each with file:line and a repro. Relay the bugs at once, but hold their fixes for the implementation batch that follows the picks. They touch the same files as the options, and two jobs that edit one file race each other. Bugs that every option needs fixed go into that batch whatever the user picks.

## UI built from the user's picks: sol finds bugs, it does not decide done

**UI work built from the user's picks: sol finds bugs, it does not decide done.** The blind reviewer never sees the picks, so it reports the picks themselves as regressions (a removed landing list, a merged button), and each "fix" adds new code that draws the next round. Drop findings that contradict a pick, or bring the trade-off to the user as one question with a recommendation. Fix real bugs (navigation that hides content, a link opening the wrong entry, tests that assert nothing). Gate done on the tests, the browser checks and screenshots compared against each pick. When patched selection or navigation logic keeps drawing new findings, restore main's code verbatim and add only the new set points.
