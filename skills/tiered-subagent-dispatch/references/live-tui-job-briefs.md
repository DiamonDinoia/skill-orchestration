# Briefs for children that run UI programs

These rules shape the brief for any child that runs a TUI or GUI end to end: capture the visible screen, exercise input, spawn agents inside it, or restart it across rounds. Verification-side pitfalls (capture commands, evidence forms) live in `references/verification-pass-pitfalls.md`.

- In a UI inspect-and-fix loop the worker and the reviewer resolve at dispatch through the ladder pick (`hermes-dispatch-route pick <kind> --tier <tier>`). Never pin a model name in the brief; resolve it at dispatch. Launch the worker as `hermes chat <flags from pick> -s <task skills> --yolo --cwd <worktree> -p <prompt>`. If the resolved session cannot start, the child stops and reports blocked; it never substitutes another model silently. Each round's findings land as one commit with the user's authorship and the reviewer model in the `Assisted-by:` trailer. The driver reverifies tests, scope and commit shape once at loop end.
- Name every throwaway install the child creates: scratch home directory, session socket name, entry artifact. A child that runs the UI on a scratch home cleans up what it copied in and what it started: the credential file gets `rm -f`d with an `ls` exit-2 proof line, and each tmux server gets killed by its socket name. Two children that alternate use of the same scratch home leave the credential in place between runs unless the brief makes deletion the last step of each. The child never starts servers or copies credentials outside the paths the brief names.
- Budget a UI piece by iteration count, not wall time. Anything past a handful of build-run-edit cycles ends a child at the harness iteration cap. Its work is then uncommitted and its review unwritten. Use one child when the piece fits one iteration budget. Otherwise split build/capture and verification: one child builds and captures, a fresh child verifies from the same fixtures. Make each child commit by file name as it finishes each step, so a cap loses at most one step's work.
- A child that inherits a capped predecessor's tree opens its report with `git status --short` plus any half-written temp files it found, before trusting or redoing anything. A failed atomic write leaves an empty temp file next to the file it meant to replace; the brief says to compare the temp file with the current content, keep whichever is the complete intended state, and delete the temp file.
- A delegated Playwright config lives in the worktree as an untracked file (e.g. `pw.r1.config.mjs`, deleted before `git status`), and the brief changes only its port, one per concurrent child (8791, 8792, 8793). A config copied into the scratch dir imports `@playwright/test` relative to its own location and dies with ERR_MODULE_NOT_FOUND: no tests ran, yet `npx playwright test --config <scratch> 2>&1 | tail -30; echo exit=$?` reports exit 0 of `tail`. The check report counts pass/fail from the log; zero tests read as blocked, not passed.
- When parallel fix children split a page's spec files (one new `test/<area>.spec.mjs` per child), the integration child widens the Playwright `testMatch` (e.g. `*.spec.mjs`) and adds one integration assertion for the property that ties the areas together. A repo config that names only the legacy spec file runs none of the new files, and CI accepts the merge untested.
- Repeated audits can report one class of visual complaint after a fix round ("boxes too large", "text too small"). Then the next brief makes the complaint a measurable DOM probe before the fix. Probe once per complaint class; skip the probe for a style-token fix. After the UI action dump each suspect rect and its text bbox as CSS px to JSON. Gate the fix on thresholds: a text box at most 40% empty at mid-run, text at least 12px at 1400px viewport and 11px at 800px. An unmeasured round spends a child's budget shrinking the wrong boxes, and the next audit re-reports the complaint verbatim.
- The audit loop converges when the manager names it: one build round and one fix round per user scale (rule T2 in skill `manager`, SKILL.md). Each round splits by page area across children (flow diagram, input bar, timeline plus layout) in parallel worktrees. Then one integration child cherry-picks the round's commits in order, and a fresh vision audit runs on the merged tree. A child never merges earlier than that. A round that ends with only low-severity findings left hands the push decision to the user.
- A vision child checks the worker's own screenshots before the commit, cap 2 rounds per area: the worker's DOM numbers say what moved, not what the page shows, and a commit that passes every test can still ship text cut off or a fill that hides what it labels. The vision query names each PNG path and asks a yes/no per defect it was sent to find; a verdict that re-words the brief without citing what the image shows is a non-verdict and goes back.
- The launcher recipe belongs in the brief verbatim, with the fallback named as forbidden: a pair of env vars that point at a built UI and a source root still leaves room for a CLI flag to start an older built-in UI instead, and an early screenshot that looks right proves nothing by itself. The recipe is reusable from the transcript of the child that first got it right; the next brief copies it instead of rediscovering it.
