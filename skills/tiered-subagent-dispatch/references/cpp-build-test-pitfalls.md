# C++ build, numeric and timing pitfalls

Load before dispatching build, test, timing or numeric-tuning work on a C++ or numerical-library repo.

- **Fits that regress a model on two parameters without guiding data stick at huge nonphysical values**. Hold suspected regimes with `fix`, or refit with a self-failure check: if any still-failing case sits in a suspected regime, mark the fit "not supported by the data at hand" and stop; do not widen the grid until the number drops.

- Timing numbers from a rerun compare with an earlier run only under the same CPU pinning and priority. A rerun under `nice -n 19` with no `taskset` on a busy box was 4x slower than the pinned baseline. When a brief reruns a timing gate, copy the baseline's `taskset`/`nice` flags from the earlier log or note. Otherwise, report the slowdown as unconfirmed, not as a regression.

- A timing comparison in a doc or PR must say WHICH commit was measured. A branch that changes prepare-time choices and timing across rounds leaves several measured states, and the 'branch' totals of one state then get quoted as another's. When two reported ratios disagree, first check they were computed on the same CSVs; each number carries its commit, per the cpp skill's benchmarking reference.

- Builds and timing never share the machine: a number measured while another job compiles is not evidence. Queue the fix or build job until the timing run ends.

- A numerical-library test sweep must cover THE USER CONFIG THAT FAILED, not only the largest one, and per-sigma from the analytic default down, not only at the locked sigma that hid the rounding term. A sweep at N=2e6 passed while N=1e3 failed, because the rounding term shrinks with N. Include the small case. Make the bound computation an overrideable function in the sweep (one line in the test's struct) so the next bound check edits no test code; hardcoding the expected bound in test code makes later real tuning commits fail the suite and leads to special-case width bumps to fit it.

- A numeric-sweep necessity decision is a two-arm probe on the same grid: arm A runs the current code, arm B runs the candidate fix, both under the same `OMP_NUM_THREADS` and priority. Count rows where A misses, B meets the contract, and the parameter A auto-chooses sits below the bound B enforces. A miss that both arms show at the same locked parameter is a different bug; do not count it for the necessity of THIS fix.

- For heuristic picks and plans, log the chosen values (sigma, width, time per phase) to stderr behind a debug env var. One child then labels each regression from a log line instead of three children building three probes. Point the env var at a file: several children inherit the same stderr.

- For every new heuristic/plan function exposed for tests, do not hand-write a lite mock. Clone the repo's existing test helper and change only the extra input. Keep a compile-time guard (double input, `throw()`) that fires if the clone drifts. A hand-written mock drifts silently and the suite passes against the wrong cost model.

- Heavy C++ builds (sanitizer/ASan, full ctest matrices) belong to ONE child. Reviewers reuse that child's results or build only the targets they need. Two concurrent ASan builds on this 62 GB box pushed memory to 53 GB and load to 15, and each one ran for more than 1.5 h. A child that exits (or that you stop) can leave its build running, so a build runs only through `terminal(background=true, notify=true)` and stops by the process rule. A name-based `pkill -f '<worktree>/build'` is never the way: it misses the `cc1plus` jobs and can hit a sibling's build. `pgrep -x cc1plus` is a read-only inventory. Before rerunning an expensive check on a rewritten commit, look for an equivalent run that already exists: a child worktree whose `git diff <base>` equals the commit's diff against the same base, built with the same flags (`grep SANITIZERS <build>/CMakeCache.txt`, pass count in `Testing/Temporary/LastTest.log`). Cite that run as the evidence, and offer the user to skip the duplicate build instead of waiting hours for it. Give ctest briefs the exact minimal configure flags, with benchmarks and examples OFF. Don't tell the child to copy the main build's `CMakeCache.txt`. That cache can have `*_BUILD_BENCHMARKS=ON`, and under ASan the benchmark translation units then run for hours with 4 to 6 GB RAM each. To test consecutive commits that differ only in tests or headers, use ONE worktree and one build dir per config. Check out the next commit there and rebuild incrementally, so the shared code doesn't compile again. A fresh worktree per commit compiles everything from scratch. Before the user asks "why so slow", check `uptime` and `free -g`, and ask the child's session for its build dirs and run time. `pgrep -x cc1plus` is a read-only hint. Report which build dirs are compiling, how long they have run, and how much memory they use.

- In Catch2 projects, ctest usually registers one entry per test binary (or only examples), so `ctest -R '<test name>'` matches nothing useful and reports a false "no tests" or a pass on the wrong set. The brief names the binary instead: `./build/test_cpp; echo exit=$?`. A tag filter (`'[relmax]'`, list with `--list-tags`) is for iteration only; the final check runs the whole binary.

- Wrap every sanitizer run (`compute-sanitizer`, valgrind) in `timeout 300`. Under memcheck, OpenMP + CUDA binaries can run for 20+ minutes with no output, and the child blocks on them. If the threaded binaries still time out, report the memcheck as timed out and rely on their passing ctests. Put this in the brief before the run starts. A memcheck counts only when the report quotes the `ERROR SUMMARY` line for each binary from the output file. A child can call its sanitizer script before it writes the file (exit 127, "No such file or directory") and still report the check as done. The brief says: write the script to a file, `ls` it, run it, and quote the ERROR SUMMARY lines.

- For adaptive meshing, convergence-gate or other sampling-based tree code, each new sampling grid is its own decision with its own normalizer, and the gates combine with AND. Pooling several grids into one norm divides by a larger count (a residual on the old grid diluted by zero-residual new samples passes a check main rejects) and pollutes any committed scale (a finite huge grid committed before a NaN on a second grid leaks the inflated scale to later panels). A gate's start or end coordinate comes from the exact panel bounds (index 0 = lo, index N = hi, interior clamped), never `center - half_len` reconstruction, which is already outside the domain for bounds that are not binary-exact. When a per-panel scale (max|f|) normalizes a relative tolerance, collect both grids' maxima before EITHER decision; running gate A on its own max and gate B on a later larger max makes the verdict depend on which grid holds the largest value, and swapping the sample layout flips it.

- A dedup or forward between feature-gated files (one SIMD arch kernel calling another, one platform backend reusing another) is safe only when every build that compiles the caller also compiles the callee. Before briefing it, read the include guard of the caller's file and the config macros that set both gates, and check whether the caller's dispatch tag inherits from the callee's. If it doesn't, the forward must name the callee's tag explicitly, or overload resolution quietly picks a slower base version. The brief's checks: build and test each gated configuration on its own (an emulator such as SDE or qemu for ISAs the host lacks), print the selected default arch, and mutate the callee to prove the caller's test goes through it.

- A strict-flag build (`-pedantic -Werror`, a new standard mode) that fails is not a branch regression until the base fails differently. Build the same probe against the base tree with the same flags, and count only the errors the base doesn't have. Header-only libraries often have pre-existing `-pedantic` hits (e.g. `__int128`).
