# Ops pitfalls (background work, delegate_task, cross-host, skill edits)

Load for cross-host work, TUI display bugs and skill-repo edits.
Load for background-process handoffs, `delegate_task` quirks, cross-host work, TUI display bugs and skill-repo edits.

- The TUI hides running children behind a collapsible dock (`LiveAgentsPanel` in appLayout.tsx) plus the `/agents` overlay; raw transcript paths are what the manager sees when the panel is not rendering. When the user says they only see transcripts, treat it as a UI bug to debug in ui-tui (mount gone from the local patch, or the roster missing cross-session children), not as a missing feature to build.

- Test scripts that a skill or repo ships write scratch output with `mktemp` and an EXIT trap (images too: a per-run tag the trap removes), never to a fixed name in the cwd or `/tmp`. A fixed name leaves untracked files in the clone and lets two runs overwrite each other. Every test brief's CHECK runs `git status --short` after the test and expects it empty; grep the skill text for `/tmp/` before a release.

- When a CLI works on one host and fails on another with the same login and config ("model not supported when using Codex with a ChatGPT account"), compare `<cli> --version` on both hosts first. An older CLI rejects models the newer one accepts; upgrade it the way it was installed (user space, old package to the attic) before changing the configured model.

- A child's "X is not installed on <host>" over ssh is often a PATH artifact: non-interactive `ssh host cmd` skips the login rc files, so `~/.local/bin` and nvm paths are missing. Recheck with `ssh host 'PATH=$HOME/.local/bin:$PATH; command -v X'` or `ssh host bash -lic '…'` before reporting a missing tool or planning an install.

- Passing checks and a PASS review do not prove the code is what the user wants. Before reporting code deliverables as ready, a subagent reads a representative changed file against the user's style skills for that language (`cpp` and any task-specific style reference), and put those rules into the child brief up front. Children write over-engineered code that compiles, tests clean and passes review (RAII wrappers around a C handle, named helper lambdas, cosmetic rewrites), and the user then rejects every branch at once.
- A child exiting 0 may have detached long work (renders, builds) into its own background process (`persist_on_release`) and reported "running, will notify". That notification never reaches the manager. The same goes for a build that a child starts with a trailing `&` inside a `terminal` command: the child gets no notification when it ends, so it waits with no output until it is marked STALLED. For long compute, put in the brief: "run the long job in the foreground of your session (generous timeout) or report `partial` with the exact command; never detach it". When a brief does allow detached work, the worker starts each detached job only through `terminal(background=true, notify=true)` and passes it to its parent with `process_manage` action `handoff`, so the notice reaches one owner. After a WORK child exits (not a routing, monitor or other housekeeping child), its launcher or monitor subagent may run `pgrep -af '<script or repo name>'` once as a read-only status hint. The output can match sibling agents or an unrelated server, so it is a hint to show the user, never the wait or kill decision.

- `delegate_task` children run in the manager's session cwd, and a worktree path in the brief does not change that. They then edit the session repo instead of the worktree the brief names. If that repo has a rebase stopped in it, the rebase state gets mixed in too. Put `cd <worktree>` for every command, plus a `pwd` before the first edit, in the goal text itself. Name the session repo as read-only. Also forbid checkout, reset and stash there, because a stopped rebase lives in it. After each child finishes, run `git status --short` in BOTH the target worktree and the session cwd. Move stray files with plain `mv`/`cp`, and undo only the hunks the child added by editing them. Never run checkout/reset in a tree that holds someone else's in-progress state.
- A child told to clean a task scratch dir deletes only its own named subdirectory, never the task-level dir a sibling also works in: one `rm -rf` of the task dir wipes the other child's mid-flight state and its pre-change baselines. Put it in the brief as `rm -rf` allowed only on the child's own dir, with the exact child dir named; never allow the bare task dir as the target.

- The manager's own terminal cwd persists across calls. A child told to remove scratch worktrees after its checks (a fit-check or base worktree) can delete the directory that cwd sits in, and the next manager-side terminal call without `workdir=` dies at `cd: <path>: No such file or directory` before the command runs. Pass `workdir=` pointing at a stable path on manager machinery calls (dag.py state changes, manifest probes) that follow a cleanup-owning child. The stored cwd is shared wider than those calls: one deleted dir bricks the terminal of the manager and of every delegate child at once (exit 126, output a lone `&&`). Recover by calling once with `workdir=` at an existing dir and recreating the missing path with `mkdir -p`; unprefixed calls work again after that.

- Create each output directory with a bare `mkdir -p <dir>` in its own terminal call before any command whose redirection writes into it. `> logs/run.log` with no `logs/` fails in the shell before python starts, so a step the child 'ran' did nothing, and the child burns turns discovering the empty log. Put the mkdir in the brief as its own step; chaining it (`mkdir -p d && cmd`) trips the approval prompt unattended.

- Unattended `delegate_task` children stall on shell approval prompts: a command with a pipe, a heredoc, `python3 - <<EOF`, a `sed -i` one-liner or a `;` or `&&` chain trips the security scan, nobody answers, and the child stops after the 5-minute timeout. Every brief says: one plain command per terminal call. Two chains stay allowed: a trailing `; echo "exit=$?"` and the `&&` push gate (in its own call). A destructive op (`rm -rf`, overwrite of a real file) in a combined command stalls at the approval prompt with no one to answer; issue deletes as their own call, or leave the leftover and report it. The trailing echo also makes every manager-side completion notice show exit 0 even when the job failed: the real status lives only in the log's `exit=` line, and a notice means liveness, not success. The brief also says: file edits only with the patch/write_file tools, interactive rebases with `GIT_SEQUENCE_EDITOR=:` (or a sed) and `GIT_EDITOR=true` (a bare `git rebase -i` waits for an editor), and on a blocked call apply the consent-block rule of `references/delegate-orchestration.md`. Read-only reviewers get the stricter form: in the session repo, which can hold someone else's in-progress state, plain read-only git only (no checkout, reset or stash there) and notes via write_file. A reviewer that must run builds, tests or repros does it in its own git worktree and its own scratch dir.

- Background `terminal` commands run under `bash -lic`, so the user's interactive aliases apply: `grep` there is ripgrep, and `grep -E 'pat'` fails with a flag error instead of filtering. A repeat-run or flake check built on a `| grep` then reports nothing. In background commands print `echo "run$i exit=$?"` per run and write full output to files that you parse in Python. `command grep` also gets the real grep. Use `tail -n N` with several files: the obsolete `tail -2 a b c` form fails with "option used in invalid context" and makes the whole background command exit 1.

- Scratch check scripts that children reuse across worktrees (marker checks, lint wrappers) must find the repo with `git rev-parse --show-toplevel`, never a hardcoded root. A hardcoded path to the first worktree made every "check passes" on later branch worktrees a pass on the wrong tree. Grep a shared check script for absolute repo paths before you name it in a brief.

- Before dispatch, `ls` every path the brief names (venvs, build dirs, check scripts, interpreters). A wrong path from memory or an old summary sends the child searching the disk, or it picks an interpreter from a read-only tree and hangs there. Name the exact working path, and steer running children at once when you find one was wrong. Then rerun the checks that used it, because earlier passes may not have used the tool you meant.

- A watch loop `while pgrep -f '<brief-name>'` never ends, because its own command line contains the pattern. Wait by the process rule. `pgrep -f` stays a read-only status hint (bracket trick, `'[f]x14-brief'`). Killing the loop later does not stop its queued heartbeats; they keep arriving out of order for hours, so answer them in one line. Stopping the old monitor per batch makes it report exit 143: that is the manager's own kill, so say so in one line and do nothing else.

- When the user names an artifact ambiguously ("the coverage PR") and two things match (a coverage bot PR vs a CodSpeed PR), search all org repos plus `gh search prs --involves @me` before answering, then report both candidates with what each is, and say which one you checked. Don't silently pick one: the user's next message otherwise corrects you and costs a round.

- A resource cap in a brief binds a host, not a command. "Wrap every heavy command in the systemd-run quota" reads to the child as wrapping its ssh calls too, and the local cgroup then throttles the remote host the cap was meant to leave alone. State the host per limit: local box inside the quota, remote render host outside it.
