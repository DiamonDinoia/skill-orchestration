# Rebase, CI and branch-shape pitfalls

Load before delegated rebases, branch splits, CI fixing and pushes.

- Rebasing onto a different base while a rebase is in progress: `git rebase --abort`, then `git rebase --onto <new> <old-merge-base> <branch>`. Give the child the old merge-base explicitly so only the branch's own commits replay, and tell it to keep both sides' intent in conflicts.

- Delegated rebases need history checks, not just tree checks. Given a messy history, children "recompose" the delta into one `tmp:` commit and drop commits, and a recompose can re-add files the fork had renamed. The brief requires one commit per original commit (same subjects, in order, no `tmp`), and the checks are in `fork-upstream-sync` (interdiff, subject diff, per-commit changed-line hashes, `git ls-files` for upstream-named files).

- After a delegated rebase, a subagent reads every conflict resolution, CI/config files first (`git diff <upstream> HEAD -- .github/ cmake/`). Children merge config by inventing a value that looks like both sides (e.g. a CI matrix arch name), and nothing local fails until CI runs it. The subagent checks each value against its consumer (the build script's accepted list). When upstream already covers the branch's intent, the right resolution is to drop the branch's hunk: `git diff --quiet <upstream> HEAD -- <file>`.

- Children "fix" formatting to match their LOCAL clang-format/linters, which can be a different major version than CI's, and the result is churn that CI's formatter may reject. Lines that passed CI's format check before the rebase stay untouched. Check `git diff <OLDHEAD> <NEWHEAD> -- <branch files>`: it may show only the intended fix plus changes from upstream. When a local tool disagrees with CI's version (unknown flags, different style), the child reports the check as tool-skewed instead of editing to satisfy it. Before every push, run each step of the repo's style workflow (`.github/workflows/*style*`) locally with CI's pinned tool version: `uvx --from clang-format==<CI version> clang-format --dry-run <files changed vs base>`, plus any include checker the workflow runs (e.g. `uv tool install diskarzhan`, then the workflow's exact command). Deleting a helper can leave an include unused, and a new expression can wrap differently under CI's formatter. Each of these otherwise costs a full CI round. When CI's formatter wraps an expression awkwardly, restructure the code (a small lookup array instead of a nested ternary) rather than commit the ugly wrap.

- "Fix the CI failure" triage is routing work, so a subagent does it before the brief: `gh pr checks -R <upstream> <pr>` for the failing job, `gh run view -R <upstream> --job <id> --log-failed > $TMPDIR/x.log`, then dedupe the `error:`/`warning:` lines in Python (one tidy error repeats per translation unit). Put the distinct errors verbatim in the brief, plus the workflow's exact repro command for the child to run locally.

- Children bypass hooks (`git commit --no-verify`) when a formatter fights them. Before pushing, a subagent reruns the hooks over the whole range: `pre-commit run --from-ref <BASE> --to-ref HEAD`. Read the failing hook's output before treating it as a failure; a staged-hunks hook can report Failed with "no modified files".

- After every child amend or commit, check that `git log -1` shows a NEW SHA and that `git status --short` is empty. A formatting pre-commit hook (clang-format on staged hunks) rewrites files and fails the commit. The child's next `git diff --stat flatiron/master HEAD` then prints the OLD commit's stat, which looks like success. The brief says: if the hook reformats, re-add those files, rebuild and rerun their tests, then amend again.

- "Is this local edit or upstream?" is checked against the CURRENT upstream (`gh api repos/<o>/<r>/contents/<path>` plus its commit list), never a local clone of unknown age. A stale clone made upstream rules look like the user's own edits.

- Splitting one combined commit into several branches (one per language or component, each off the same base): the check is that the union of the branches equals the combined commit. Merge the branches into a scratch worktree, then `git diff <combined sha>` there must be empty. Each branch also builds and passes its own tests alone, because a split can move a test or a CMake entry away from the file it needs.

- The inverse split (one scattered fix becomes one cohesive branch): the check is that composing the branches in review order equals a reference branch that stacks them all (`git diff <ref> <final>` empty), because one commit's code can sit in another commit's layer (a helper built on a later refactor, a test that uses a later constant). Compose them in the order they will be reviewed, not in the order the work landed. A commit that cannot stand on the shared base alone goes later in the order, or its base gets folded in.

- When every job is cancelled before its first step with "The job was not acquired by Runner of type hosted", merge-when-green stops with `bad=['CI']`, but the code never ran. Check the Actions component (`https://www.githubstatus.com/api/v2/components.json`) before any triage. During an incident, one background loop waits for `operational` at the user's check cadence, then reruns `--failed` and relaunches merge-when-green; hold deploys and releases that depend on those merges until then.
