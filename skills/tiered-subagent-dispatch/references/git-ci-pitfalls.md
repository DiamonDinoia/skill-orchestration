# Rebase, CI and branch-shape pitfalls

Load before delegated rebases, branch splits, CI fixing and pushes.

- Rebasing onto a different base while a rebase is in progress: `git rebase --abort`, then `git rebase --onto <new> <old-merge-base> <branch>`. Give the child the old merge-base explicitly so only the branch's own commits replay, and tell it to keep both sides' intent in conflicts.

- Delegated rebases need history checks, not just tree checks. Given a messy history, children "recompose" the delta into one `tmp:` commit and drop commits, and a recompose can re-add files the fork had renamed. The brief requires one commit per original commit (same subjects, in order, no `tmp`), and the checks are in `fork-upstream-sync` (interdiff, subject diff, per-commit changed-line hashes, `git ls-files` for upstream-named files).

- After a delegated rebase, a subagent reads the CI and config hunks only (`git diff <upstream> HEAD -- .github/ cmake/`). The other conflict resolutions ride on the per-commit history checks. Children merge config by inventing a value that looks like both sides (e.g. a CI matrix arch name), and nothing local fails until CI runs it. The subagent checks each value against its consumer (the build script's accepted list). When upstream already covers the branch's intent, the right resolution is to drop the branch's hunk: `git diff --quiet <upstream> HEAD -- <file>`.

- Children "fix" formatting to match their LOCAL clang-format/linters, which can be a different major version than CI's, and the result is churn that CI's formatter may reject. Lines that passed CI's format check before the rebase stay untouched. Check `git diff <OLDHEAD> <NEWHEAD> -- <branch files>`: it may show only the intended fix plus changes from upstream. When a local tool disagrees with CI's version (unknown flags, different style), the child reports the check as tool-skewed instead of editing to satisfy it. One pre-push pass per batch covers style and hooks together. In the pass, run each step of the repo's style workflow (`.github/workflows/*style*`) locally with CI's pinned tool version. For clang-format that is `uvx --from clang-format==<CI version> clang-format --dry-run <files changed vs base>`, plus any include checker the workflow runs (e.g. `uv tool install diskarzhan`, then the workflow's exact command). Deleting a helper can leave an include unused, and a new expression can wrap differently under CI's formatter. Each of these otherwise costs a full CI round. When CI's formatter wraps an expression awkwardly, restructure the code (a small lookup array instead of a nested ternary) rather than commit the ugly wrap.

- "Fix the CI failure" triage is routing work. When the failing run names one job, brief the fix child straight from `gh run view -R <upstream> --job <id> --log-failed > $TMPDIR/x.log`. Dedupe the `error:`/`warning:` lines in Python first; one tidy error repeats per translation unit. Put the distinct errors verbatim in the brief, plus the workflow's exact repro command for the child to run locally. When several jobs fail, a subagent does the triage first: `gh pr checks -R <upstream> <pr>`, then one `gh run view` per failing job.

- Children bypass hooks (`git commit --no-verify`) when a formatter fights them. The same pass reruns the hooks over the whole range: `pre-commit run --from-ref <BASE> --to-ref HEAD`. Read the failing hook's output before treating it as a failure; a staged-hunks hook can report Failed with "no modified files".

- A formatting pre-commit hook (clang-format on staged hunks) can rewrite files and fail the commit. The next `git diff --stat flatiron/master HEAD` then prints the OLD commit's stat, which looks like success. When the pre-push pass hits that, re-add the rewritten files, rebuild and rerun their tests, then amend once.

- "Is this local edit or upstream?" is checked against the CURRENT upstream (`gh api repos/<o>/<r>/contents/<path>` plus its commit list), never a local clone of unknown age. A stale clone made upstream rules look like the user's own edits.

- Splitting one combined commit into several branches (one per language or component, each off the same base): the check is that the union of the branches equals the combined commit. Merge the branches into a scratch worktree, then `git diff <combined sha>` there must be empty. Each branch also builds and passes its own tests alone, because a split can move a test or a CMake entry away from the file it needs.

- The inverse split (one scattered fix becomes one cohesive branch): the check is that composing the branches in review order equals a reference branch that stacks them all (`git diff <ref> <final>` empty), because one commit's code can sit in another commit's layer (a helper built on a later refactor, a test that uses a later constant). Compose them in the order they will be reviewed, not in the order the work landed. A commit that cannot stand on the shared base alone goes later in the order, or its base gets folded in.

- When every job is cancelled before its first step with "The job was not acquired by Runner of type hosted", merge-when-green stops with `bad=['CI']`, but the code never ran. Check the Actions component (`https://www.githubstatus.com/api/v2/components.json`) before any triage. During an incident, one background loop waits for `operational` at the user's check cadence, then reruns `--failed` and relaunches merge-when-green; hold deploys and releases that depend on those merges until then.

- A single cancelled leg in an otherwise green run is not a defect until its cause is named. Read `gh run view <id> --json jobs` and the workflow's concurrency block: `cancel-in-progress` on a newer push of the same ref supersedes the older run, a fail-fast sibling cancels the rest of a matrix, and a runner reclaim leaves no job log. Only a cause inside the repo gets a fix; the rest reruns with `gh run rerun <id> --failed`.

- A CI fix loop on legs no local host can run (Windows, macOS, a cross target) carries its stop rules in the brief: a push budget, a stop when the same first error survives two fixes, a time cap, and a per-round table in a scratch log (push sha, run id, per-job result, first error, fix). Each round classifies the failure as ours vs infra (runner image, network) and as newly exposed vs pre-existing; an infra-only failure gets one `gh run rerun --failed`, never a code change. The brief forbids dropping a test step, job or matrix entry, adding `continue-on-error`, and marking a failing test expected-fail: a silent CI is not a fix.
- On a repo created minutes ago, `gh run list` can show zero runs for the push that carries the workflow file: GitHub registers a brand-new repo's first runs late, and a child that checks in the same minute reports 'no workflows, nothing to wait on' while a run is queued. Re-check with `gh run list` or `gh api repos/<o>/<r>/actions/runs` before reporting absence, then attach `gh run watch <id>` once an id exists.
