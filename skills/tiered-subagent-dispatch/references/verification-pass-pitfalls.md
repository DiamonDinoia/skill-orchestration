# Verification pass pitfalls

These bind the manager's final verification and blind-review steps.

- A verifier's cited file:line is a claim about the diff base the reviewer read, not about the current tree. The fix brief gives the fix round ONE precondition check. Confirm the claim on the CURRENT diff (`git diff <BASE> -- <file>`, read the cited line). Probe only a finding that names runtime behaviour; the probe rules are in `references/review-loop-rules.md`. A review that runs after earlier fix rounds often cites line numbers from a pre-fix file. The child edits by content, not by the stale line number alone.
- When a review names a defect pattern in several repos (a lock, a gate, a refresh step), check only the repos the review named. Check all against the same rule. Report a yes/no table with file:line. No alignment child per pattern and no scan of repos the review did not name.
- A combined cross-repo review's findings about on-disk layout (nested paths, missing dirs) can be artifacts of how the combined patch was built. Fold the `git ls-tree` / `git remote -v` confirmation into the fix child's step 0, per worktree, before the fix is shaped.
- A child's frame for a compile-time property ("X is not constexpr", "the compiler forbids it") is a hypothesis, never a fact for a fix decision. Settle it with one `static_assert` probe on one compiler before the fix is shaped. Mark the other compilers unverified. A fixer once dropped `constexpr` from a branch whose builtins keep it constant-evaluable on that claim.
- A mutation run that stops only at `timeout` with 0 bytes on stdout is a reporter hang, not a slow test. doctest blocks at 0% CPU after the first failing CHECK inside a template-instantiated `TEST_CASE_TEMPLATE` that still holds a live context scope. The mutation verdict comes from the first ERROR line, not the exit code; confirm against the unmutated binary (same filters, under a second).

- Before spending a Sol review round on a route nobody has pinged, run the readiness probe ONCE per task, not per review round. Resolve the sol id live (`hermes-dispatch-route latest sol`). Send one tiny `hermes chat --provider openai-codex -m <resolved id>` ping expecting a fixed reply (PONG). Read the gateway's request-dump env (`HERMES_DUMP_REQUESTS` in the live gateway pid's `environ`). The probe separates the three failure classes a blind round would otherwise read as one dead gate: OAuth/auth dead, the route's cached id rejected by the provider, or the dump mechanism unarmed (verdict isolation unverifiable). The ping is the one check that runs on the checked route's own provider. Also ping `hermes-adversarial-review --help` for its current flags before briefing a review round on a script patched earlier in the session.

UI, integration and live-system verification (evidence a fresh session can check without trusting the author's word):

- Briefs for children that run UI programs end to end are in `references/live-tui-job-briefs.md`: scratch-home and credential cleanup, iteration-cap budgeting, the launcher recipe.
- A vision model routed through a `hermes chat` child may answer from the prompt's own descriptions without calling the image tool, then admit it, and its image calls can hang unpredictably. For text-on-screen evidence (dock rows, menus, typed input) prefer deterministic capture over vision judgment: `tmux capture-pane -p` into a file and `grep` the line, with the grep hit printed verbatim. Reach a vision model only for genuinely visual properties (layout, color, occlusion), and check the answer quotes image content; a verdict that paraphrases the brief is a non-verdict. Accept one non-verdict and report the missing evidence; do not send it back for another pass.
- A plot or figure generated by a text-only child gets visually inspected by a vision child when the report shows it to the user. A PNG can look right in the numbers and be unreadable. Route the image to a `vision` child (`hermes-dispatch-route pick vision`) with the PNG path pinned in its prompt. A plot the report never shows gets the numbers check only. The vision child's verdict names what it sees in the image (six series load), not whether the data are plausible.
- The steer timing rule is in SKILL.md. An urgent reversal (drop a wrong lane) that cannot wait for the current call goes as a stop plus a fresh self-contained brief; a long steer the mid-flight call cannot see wastes the call.
- Timings taken under an ISA emulator (SDE, qemu user-mode) are never evidence: they can be off by orders of magnitude. Perf gates run natively only; SDE output is for correctness, never timing.
- Live-acceptance runs must launch the real artifact, not a fallback entry point: a CLI flag like `--tui` can start an older built-in UI and never load the build under test, so every screenshot then judges the wrong program. The brief names the exact entry artifact (the built entry file path) and has the child confirm that path at startup before any capture.
- A unit test cannot check behavior tied to the real terminal size: in tests the renderer sees a fixed-width stdout, so width-dependent layout (label budgets, truncation at N columns) verifies only on a live capture at the real pane size. Name the column widths the brief wants verified as live-capture checks; keep unit tests for the non-width logic.
- A vision-model audit of a UI (a vision-routed child reading screenshots) reports impressions, not measurements. Triage only MAJOR visual findings before any fix dispatch, and log impressions as follow-ups. The triage for a MAJOR class is a deterministic measurement with Playwright `page.evaluate` against the live page. Compute the WCAG contrast ratio of the two real computed colors. Or walk the ancestor chain to check whether anything with `overflow: hidden` cuts the element. A viewport-edge cut on a scrolling page is not a defect. Vision stays the right tool for genuinely visual judgment (balance, clutter, occlusion); measurement is the right tool for every quantitative claim. The animation variant of the same rule: a script that compares the bounding boxes of every non-token element across early/mid/late frames beats any vision verdict about "things moving".
- Two captures of a live view can be identical without a bug: a transcript that appends only when a tool call finishes shows no change while the child sits inside one long call. Before reporting a staleness defect, capture a tail update across a tool-call boundary, not across a fixed delay.
- Lifecycle state changes flip views: an open detail or chat view can switch away on its own when its subject leaves the live roster, before the user reads the final state. A brief that asks whether the user sees the last event gets the capture taken after the subject finishes with the view still pinned, not during the run.
- A blind reviewer never receives the author's rule list, so it flags the project's author exceptions as bugs. Feed each project's own exception list to the fix children and the fresh verifiers as their own checklist, one line each. Keep that list in the project it belongs to, not in this reference. An earlier version of this file carried one project's list here; those items now live with their project.
- The file-mutation verifier can refuse a child's write (unread fixture, wrong dir), so the run that follows may have used a stale fixture. When a report shows a refused write, the verification child reruns that check once and the manager records the refusal in the report. Never trust the mutation claim that came with the refused write. Skip the mutation rerun.
- Build a review patch from COMMITTED ranges only (`git diff <base>..HEAD`), never a working-tree diff. Put the task's committed file list in the review brief, plus the user's known uncommitted files in a context header. Do not gate per finding and do not triage dirty-file findings. A combined diff that sweeps in the user's dirty files cannot send a fix round onto code the task never wrote.
- When a file in the review diff holds a secret line, redact the VALUE in temp copies and keep the diff. Do not exclude the whole file, or the rest of that file escapes review.
- A hook script moved or rewritten for one harness must resolve its own skill source, never read a sibling harness's install path: a Codex hook grepping `$HOME/.hermes/skills/...` breaks every Codex-only machine the dotfiles land on. The hook locates its own copy (same repo, its harness's skills dir) and falls back silently when absent.
- A fresh verifier NEVER edits the worktree under review: it works on a `cp -r` copy (or mounts the worktree read-only in its container), because a blind review may read the same worktree at the same time. It runs one mutation the author never ran, picked from the design rules, unless the author's mutation list already covers the changed functions.
- A packed tool meant to install or run outside its development clone must prove itself in the shapes it ships as. Tests for a hook, CLI or interpreter that read git history at run time (`git show <sha>:<path>`, comparison fixtures pulled from the clone's object database) pass in the dev clone and fail in a shallow clone or a `git archive` export, which are the shapes a `pip install` user actually has. The fix brief for that class pins the expected output as a checked-in fixture (generated once from the same payloads). When the fix touches history-reading code, run the suite in both shapes. Use a `git clone --depth 1` and an `git archive | tar -x` of the branch tip. Otherwise run the dev-clone shape.
