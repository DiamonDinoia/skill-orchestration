# Mutation and test-double pitfalls

Load before dispatching test-writing work, and rerun at verification.

- A mutation check proves only the entry point it mutates. Children that add test coverage often break a function the old tests already cover, so the new test lines stay unproven. In the brief, require one mutation per newly covered function or path. At verification, the verification subagent reruns a mutation on the exact function the new test calls (copy the source file, inject a one-element write, rebuild only that test target, expect FAIL at the new line, restore, expect PASS). For a crash fix, the regression test must cover the path that crashed, not a sibling entry point. A test on entry A (null plan) passes while the crash was on entry B (valid plan, failed setpts). Before you accept the fix, a subagent removes the guard it names and reruns the test: it must fail or segfault. If it still passes, the test does not cover the fix. A mutation that fails no test is itself a finding: the manager adds a test-gap deliverable whose case has one assertion that names the invariant the mutation broke, and the same mutation then proves the new case.

- The runtime's file-mutation verifier can report a FAILED edit on a test double mid-run (a fake harness binary). Every check the child ran after that write may have used a stale test double. The child report can still claim the checks passed. Never accept those claims. The verification child rebuilds every test double itself in a fresh dir and runs a positive control first (the fake tool must log its argv and exit nonzero; prove it intercepts a call before accepting 'no call happened'). Recipe for a no-network selftest harness: `references/no-network-selftest-harness.md`. Tests must exercise the real output, not a copy of it. Children write a helper in the test that rebuilds the row/frame/string "the way the component does", and the test then passes while the component is wrong. The same happens inside one file: a self-check calls `fitRow` while the UI calls its own `Panel.fit`, and the child's report says the UI "renders through" the tested function. The verification subagent greps that the logic has ONE definition and that the render path calls it. The brief requires the test to render the real component (or call the exact function whose output is printed), forbids any re-implementation in the test file, and lists one mutation in the component's own rendering (reorder, drop padding, freeze state) that must FAIL. A mutation check leaves stale artifacts. Children revert the mutated source and don't rebuild, so the test binary in their build dir still holds the mutation. If you rerun it, you get a false FAIL, and the child's final "tests pass" never ran on the reverted code. The brief requires a rebuild and rerun after every revert. Before you trust or reuse a child's binary, compare its mtime with the newest in-scope source (`stat -c '%y' <binary> <sources>`). If the binary is older, rebuild it or probe the committed tree (`git archive <sha> include | tar -x -C $TMPDIR/x`). The same applies to every new assertion in a fix commit: run it on the unfixed base. An assertion that passes both with and without the fix (e.g. `REQUIRE_THROWS_AS` on behaviour that already existed) is a characterization, not a regression test. Tell the user which it is. Output sentinels in "writes nothing" tests must be distinct nonzero values (1.25, 2.5, 3.75), and the mutation writes `0.0`: a zero-initialised buffer passes a stray write of the most common value. Numerical guard fixes (reject NaN/inf, overflow, degenerate degree) get a CHECK that calls the checker function directly on controlled inputs, with an isolated NaN and an isolated inf at each position, plus an audit table of every `std::max`/`std::min`/accumulation in the diff, src and tests alike. `std::max(x, NaN)` returns `x`, so a NaN dropped by a later finite value survives an end-to-end fit test, and the next review round finds the same class again. Test helpers that normalise errors divide by the true scale when it is nonzero; a `max(scale, 1)` clamp turns a relative check into an absolute one for |f| < 1.

- Tests in a copied worktree (a mutation copy made with `cp -r` of repo plus `.venv`) run as the copy's interpreter, `<copy>/.venv/bin/python -m pytest`, never through the copied `.venv/bin/pytest` script. That script's shebang hardcodes the original worktree's interpreter, so the run silently imports and tests the SOURCE tree and a mutation passes as a false green. A mutation run that comes back green without proof it imported the copy is suspect: have the child print the tested module's `__file__` and check it sits under the copy.

- The literal scenario test can miss the mutation. A test that replays the finding's exact steps (untracked at first Stop, staged at second, an edit later) passes the fix and also passes the bug when the assertion only checks final emptiness: the bug's wrong output and the fix's right output both end empty on that path. Pair each scenario with one assert that names the thing the fix changes (the saved extent, the decoded name), and rerun the mutation: a mutation that still passes means the assert, not the scenario, is what must fail it. Prove each mutation failed a test; a mutation that fails none is itself a finding (the new test has no teeth), and gaps of that class get their own one-assertion deliverable before the round closes.

- A dedupe fix carries at least two independent mutations, one per thing the fix decides: removing the dedupe lookup must fail the repeat-call test, and widening the dedupe key so unrelated rows collapse (keying on the text alone, not on its caller) must fail the separate-callers test. Only the first proves the lookup exists; only the second proves the key is tight. Name both in the fix brief; a single 'remove the dedupe' mutation can pass even when the key silently merges two different callers' identical questions.
