# Review loop rules (blind review depth)

Load when running or closing an adversarial review loop (step 7 of the dispatch procedure): fix rounds, contested findings, stop conditions.

## Review order and policy

**Policy (user mandate; skill `manager`, rules T1, T2, T5).** One combined reviewer per change set. No reviewer chains. Review output carries only BLOCKER and MAJOR findings. The round budget is one review, at most one fix round, one re-check of the fixed findings only. Then ship or ask the user. A PASS-WITH-NITS closes the task with follow-ups logged. Never run two stacked reviews per deliverable. Never respawn fresh reviewer subagent teams. Never reopen work for PRUNE or NIT findings.

**Order.** Once the deliverables pass their checks, the review runs in this order: one flatiron principal review of the change set, then sol, then report. Sol runs only after that review is clean and stays the last review. Small diffs get sol alone.

**Flatiron principal review.** Resolve the route at dispatch time with `hermes-dispatch-route pick KIND --tier principal`. `KIND` is one of `code`, `debug`, `frontend`, `research`, `prose`, `mechanical`, `vision`. Use `code` for a code review and `prose` for a docs review. The pick is anchor-first and moves with load. It is not the top rank. When the user asks for the top-ranked healthy flatiron model, take it from the rank map of `references/flatiron-routing.json`. A higher rank value means stronger. Never pick by `routes` list order; that order encodes a preference, not strength. The reviewer is a fresh `hermes chat` session with the flags of the pick (high reasoning, `-s manager`, team, brainstorm) plus the project's own skills. It never resumes the author's session. Its brief starts with the review block of `references/kimi-review-block.md`, and holds the goal, the change, the diff, the file list and the checks. It never holds the author brief, the author reports or the manager notes. The manager runs reviews and principal work as `hermes chat` jobs with the picked flags, never as `delegate_task` children.

**Fix deliverables.** Findings become fix deliverables for the author session. Only fix rounds resume the author session. Append the review block of `references/kimi-review-block.md` to the fix brief too; those briefs tend to go out without it. NIT and PRUNE findings never start a fix round: log them as follow-ups.

**Fallback models.** A job that lands on a fallback model keeps working and is flagged at the top of the manager's report. A review that ran on a fallback model does not count; the job escalates. A paid model is a named escalation, never a fallback rung. A tier's fallback never lands on a paid Claude model unless the user named it.

## Review scope and verdicts

User rule: every adversarial review (sol and Kimi) also flags useless churn and code that can be deleted; less code is preferred. Sol's fixed prompt in `hermes-adversarial-review` (INSTRUCTIONS) and `references/kimi-review-block.md` both carry this; keep it there when editing either. Log churn and deletion findings as follow-ups; a PRUNE never starts a fix round. Exit 0 PASS / PASS-WITH-NITS, 1 FAIL (BLOCKER/MAJOR present), 2 run error, 3 isolation breach.

An exit 3 with `no request dump found` is a tool fault, not a verdict. Retry the real review at most once more; after two discards on the same diff, stop and ask the user whether to ship on the other checks. Never relax the fail-closed isolation check to get a verdict. Known persistent cause (diagnosed 2026-10): `hermes chat` runs each turn inside the long-running gateway daemon. The per-request dump the script's isolation guard expects is not written where the guard looks. On that signature stop without a third retry, defer to the private HERMES_HOME tenant route of skill `manager`, references/fix-rounds-and-reviews.md. It counts as a real verdict. Mark the blind review waived (not passed) in the report only when that route also exits 3. Gate on the other checks until the script is adapted.

## Combined (coherence) review

**Combined (coherence) review across repos and snapshots:** the script takes one `--repo`, so build one patch and pass `--patch`. Concatenate `git -C <repo> diff -U15 <BASE> HEAD --src-prefix=a/<repo>/ --dst-prefix=b/<repo>/` per repo, plus `diff -u -U15 --label a/<name> --label b/<name> <snapshot file> <live file>` for each non-git path (skip the snapshot's `.manifest.json`). Write the result file with `echo "exit=$?"`. Run only the combined review when the change spans repos or snapshots; otherwise run the per-repo review only.

A finding that rests on something outside the diff (a plugin hook that replaces a removed config entry) is checked against that real mechanism; reject it with that evidence in the report, never on reading alone.

An exit 3 with "user payload is not exactly the diff query" on a diff that holds secret-shaped text (`*_API_KEY=`, `*_TOKENS=`) comes from Hermes' request-dump writer, which redacts the on-disk copy but not the wire request. The script now also accepts the query passed through the same installed redactor, and fails closed if it can't produce that copy. If it recurs, write the dumped user text and the query to files, find the first differing byte offset in Python, and fix the comparison; never weaken the one-user-message, no-tools, no-marker checks.

On FAIL: dispatch the fixes through the ladder, then review again (fresh run, same BASE). Cap the loop at one rerun; then take it to the user. Relay the review file path and the verdict to the user. When a tool's own text output is the verdict, `sha256sum` the tool before dispatch and again at read-back: a tool that changed mid-run is a changed instrument, and the run's evidence goes with it.

- **Sol re-review gates on fix-round regressions too.** The gate is the goal findings plus regressions the fix round itself introduced (four of the manager skill's MAJORs in one round landed in text the previous round had just added). A re-review that finds only new defects inside freshly touched lines is a FAIL on introduced regressions, not fresh scope; the fix round count covers them.

**Prompt-level review outside the script.** `hermes-adversarial-review` reviews a diff. When the artifact is the prompt or skill text itself, and citations in it must be checked against a live upstream clone, sol runs as a plain oneshot job: `hermes chat --provider openai-codex -m <sol id> --reasoning high --yolo --oneshot -Q --max-turns 80 --query-file <brief>`. The user's effort cap for sol is high, never max. Tools stay on (`--yolo`) so the reviewer reruns citations against the pinned clone; the brief names the reviewed files with their sha256 and forbids writes to those files or the branch. They can write scratch files and prototypes. The blind rules still hold: the brief carries the review dimensions, never the author's intent, subagent reports or the fix history, and findings return verbatim into fix briefs, unattributed.

## No goalpost moving

**No goalpost moving (standing rule; user-directed).** The brief of every Sol re-review (and every first review that follows a fix round) enumerates the goal findings: the verbatim quotes of the findings that spawned the fix round. The verdict gates ONLY on those findings remaining unfixed or on regressions introduced by this fix round. Log every other BLOCKER or MAJOR Sol raises (new findings on untouched code) verbatim to the follow-up spec. MINOR, NIT and style findings never start work and never gate (skill `manager`, rule T1). Push/shipping decisions treat goal-fixed + new-side-findings as PASS-with-followups.

## Fix briefs name the class, not the instance

**Fix briefs from a review name the CLASS, not the instance.** Sol cites one or two files per finding; children fix exactly those and the next round finds the same bug in siblings (or in code the fix itself just added). Every fix brief says "fix this class everywhere in `git diff BASE HEAD`" and its CHECK is an enumeration: every site of the pattern with file:line and how it is now handled, plus a grep/script that returns nothing when the class is gone. If a second round finds a class the first round claimed fixed, escalate that deliverable one rung (`pick --failed`). That escalation is the deliverable's last round. A fix to shared parsing or classification code gets whole-family probes, in the fix brief AND in the review block. A probe that enumerates the family from real assembler output finds that class; one that reruns only the originally reported lines does not.

## False positives need a run

**Never dismiss a finding as a false positive on reading alone.** A header declaration plus "CI passed before" is a hypothesis, not proof, and the user asks for it to be run. Run the probe only for a finding that would change code; report the rest as opinion. Dispatch a verification child in a separate detached worktree (`git worktree add $TMPDIR/<task>-wt <HEAD>`), so it runs in parallel with the author's fix round in the main repo. Its brief: build the exact path the finding names (cross-arch via the qemu user-mode emulator at each vector length CI uses), add a probe that pins the claimed type/behavior (`static_assert(std::is_same_v<decltype(...), ...>)` plus runtime asserts on edge values), confirm the arch-specific kernel is the one selected, and run one mutation to prove the probe can fail. Report the verdict to the user only from that run.

## Push gate

**Don't push while the verdict is FAIL**, even when you judge every remaining finding a false positive or a style opinion, and even when the original request ended in "then push": that covers a clean result, not a FAIL. That judgment is the user's call: report the findings with your recommendation and ask first. Then the fixes get amended in. The fix round's own re-check of the fixed findings is the review before the push; no extra run. Then the one push (`--force-with-lease=<branch>:<last pushed sha>`).

## Contested findings: majority vote

**User rule: contested findings go to a majority vote.** Findings that are opinions or unverifiable from the diff (refactors, "is this abstraction needed", platform-baseline questions) are settled by three independent reviewers from different model families: the healthy Kimi, the latest Sonnet and the latest sol, launched in the same turn. Each gets one ballot brief (copy per reviewer with its own scratch dir), a read-only detached worktree at the reviewed HEAD, the findings as written, what to weigh for each one, and the findings already settled by experiment marked as excluded. Each one answers in exactly `Fn: FIX|KEEP - <evidence it checked itself>`. Fix a finding only on 2 of 3 FIX votes; report the tally per finding. Findings that an experiment can settle get the experiment, not a vote. When voters split on a FACT (e.g. "master already fails at -mcpu=power7" vs "master's ops are never instantiated there"), the vote does not settle it: a subagent runs the decisive repro on base and head (same flags, the exact type the claim names) and the manager acts on that. Before overriding a KEEP majority with a fix, a subagent also compiles the proposed fix's END STATE on that target: a guard that routes to a fallback can fail the same way through the fallback's own dependencies, and then the fix adds code and fixes nothing. Spend the three-reviewer vote only on BLOCKER and MAJOR findings; the manager settles MINOR and NIT findings directly.

## Which findings get fixed

**User rule: fix review findings only in code the branch introduced.** Before briefing a fix, check it with `git blame -L <a>,<b> <file>` or `git diff BASE HEAD -- <file>`. If the lines come from the branch's commits, fix them in the amend. If they are pre-existing upstream code, leave them and say so in the report. Never brief a NIT fix; log each NIT as one report line.

**When the review corpus is a rebased commit stack of already-shipped patches** (not one task's fresh diff), the verdict's FAIL flag does not map onto the introduced/pre-existing split on its own. Gate on the produced tree, not on finding severities: decide whether the tree passes its checks and the review of what the rebase itself changed. Then run the intro triage of this file on the FAIL-flagged findings only. Mark each per owning patch and provenance (pre-existing in the live patch set, or introduced by the rebase or this task). The user decides which pre-existing findings land in the same rollout, since the review is the read the tree gets; sort them by the triage into one decision list: introduced now, pre-existing A-class (ordinary use), pre-existing B or C class. Never find pre-existing defects live on the install, stay silent, and ship the update anyway.

**User rulings on findings are standing.** When the user says a class of finding doesn't matter (or picks a specific fix style for it), write it into the task's spec file as a standing rule, steer or re-brief any child already working on it, and on every later review drop that class silently instead of dispatching it. A child fix for a ruled-out class gets reverted before the next review.

**A finding that reverses an earlier round's fix** (round N asks to add a restriction, round N+2 says the restriction hides real problems) is a design trade-off, not a bug. Take the later round's direction as the fix and record the earlier finding as a documented limit. Do not flip the line back.

A child's review-round cap is 2: the review and the re-check of rule T2 in skill `manager`. The brief names the cap. The manager counts the review files it writes (`<task>-review<N>.txt`) and takes the report when the cap is reached.

## Bound the loop

**Bound the loop.** The round budget of skill `manager`, rule T2 binds every loop. One review, at most one fix round, one re-check of the fixed findings only. Then ship or ask the user. The counters below bound only rounds the user approves past that budget.

Budget the loop by what the next round pays, not only by the round count. Fix at most 2 mechanism-class findings per task; then hand the rest to the user. A round whose confirmed findings are all "unusual setup" or "doc" ends the loop as documented limits plus a user decision. This holds when its fixes carry a wider blast radius than their trigger.

One design keeps failing review on new edge cases of itself (each fix exposes the next width/timer/overflow case): stop patching that design. Write one fresh spec whose design closes the classes structurally (fixed widths, decisions from the worst case, truncation at the symbol), and keep the failed design's tip on a `backup/` branch so the reversal is cheap. One redesign per task; further failures go to the user as options.

The surviving design keeps failing review only because each new mechanism it tries draws its own MAJORs: stop at the round budget of rule T2 in skill `manager`. Close every BLOCKER in the one fix round. Confirm or reject each new MAJOR that gates a fix on the code (a fresh read-only subagent, not the author's say-so). Fix the confirmed ones and hand the user the still-open findings with options instead of another round. A fix loop needs a closable end condition (named limits accepted), not "one more round". An accepted named limit becomes a one-line comment at the code site (`# shortcut: <the limit>, <when to upgrade>`); an undocumented limit re-surfaces as a new finding in the next round.

A round whose only accepted findings need an unanswered user question or an outward-facing step (push, publish, a config the router must not touch) ends the loop as pending user input, not with another round. Land the reversible fixes, report the verdict with the open items, and dispatch no further fix round until the user answers; otherwise the loop manufactures churn while its real blocker sits in the user's queue.



Probe only a MAJOR that contradicts the checks' own output: run its claim once against the real code before branching next steps. A MAJOR the checks support needs no probe.

Rotate the review family when one scope reaches a third review round; fresh sessions from one family can repeat the same blind spots. That rotated round is final: take open findings to the user.

A fresh FAIL with more than 3 findings of mixed machinery and prose gets one read-only triage child before any fix brief. The child reproduces each finding that is not doc or cosmetic (smallest probe). It classes each finding by impact (wrong result or paid-quota loss in ordinary use; needs an unusual setup; doc or cosmetic). It asks `which commit introduced the cited lines`. Introduction is judged against the task's original BASE or snapshot, and prior execution in an installed copy exempts nothing. Fix briefs follow the introduced-and-impactful classes first. Pre-existing or missable classes get their own fix branches inside the original final review range. Never mix them into the introduced-fix brief, so the gate's next blind run does not re-digest them.

The rerun keeps the same BASE, so a fixed pre-existing finding reappears in the next review file unless the child proves its provenance. The verdict follows the goal-findings split of this file: fixed introduced findings stay fixed; pre-existing findings that stayed on the user's list stay open; the rerun's other BLOCKER counts as FAIL. A finding with intro evidence quoted from the triage (the old patch file line) is triaged, not a new finding.
A capability probe finding (a vision or web probe that guesses) gets its own design input first: the probe must use only-live input with at least two controls and treat an empty, truncated or refused answer as inconclusive, never as a stored false. Each fix brief's CHECK must exercise the new code path, not just rerun the suite.
One fix round per deliverable, then one re-check of the fixed findings only (skill `manager`, rule T2). After a FAIL, sort findings into introduced-by-branch vs pre-existing (visible as unchanged context in the diff). If only pre-existing or MINOR items remain, stop and ask the user whether to push or ship with documented limits. When the user is unreachable, ship nothing and push nothing. A later round runs only on the user's approval, and the brief declares it the last. If it still produces a real new finding, stop and push nothing. Report the findings, the measurements so far, and the options. Opinion or taste findings never buy a round.
Findings on edits the user made in their own original commit (scope churn, a changed default, a deleted README section; check with `git diff BASE <user's commit>`) are user intent: never brief a fix for them, bring them to the user. The same holds for the user's existing config that a job only moved into a repo as-is (permission lists, machine paths). Ask once with a recommendation and record the answer as a standing ruling.
A file that draws new findings three rounds running gets split out of the push or redesigned, not patched again. Cap the redesign at one. Send the user question once and state the default; an unanswered send is the decision to proceed with the reversible default.
For code that validates external input (a downloaded index or manifest), the structural close is verification, not parsing: accept the input only when its size and hash match published integrity metadata (an apt Release file lists the SHA256 and byte length of Packages), then extract with a simple regex over the verified text. Two paths that must agree, such as a dry-run plan and a live-run plan, share ONE planning function; the run prints or executes the same plan, never a second copy.
A review verdict can rest on a path inside a CONCATENATED diff (a/REPO/... prefixes) that does not exist at any repo root. The launcher's report says whether each per-repo finding's file:line resolves in the repo itself; stray combined-diff paths get marked as diff artifacts, not shipped to fixers.

Bound the loop by the commit range too, not only by the round count. A review whose BASE sits before the user's feature commits keeps flagging the user's own design choices as findings (hook shape, memo fields, an external tool the feature calls by design), so every round fails and the fix children keep churning user intent. Widen BASE past the user's last authored commit once, as the blind-review rule already says; if the FAILs continue, stop the loop after the round that follows the widening, list the open findings as documented limits with file:line, and hand the push decision to the user.


## Parallel fix rounds by subsystem

A FAIL with findings in several independent subsystems of one branch fixes in parallel. Cut the findings by subsystem. Give each group whose fixes touch disjoint files one fix child, in its own worktree on a new branch from the FAILED head. Never branch from a sibling's branch. Each brief carries its findings verbatim, an exclusive file-ownership list, and the sibling-owned files it must not touch. It also carries the rule that a finding fixable only in a sibling's file returns [ESCALATE-TO-MANAGER] instead of editing across the line. Each child verifies its sha at step 0 against the failed head. A single-owner resource stays single-owner across the round (one Playwright port, one device): every brief names its one owner. When one fix adds an API another fix should consume, neither child crosses the ownership line to wire it. The merge node wires it after both sides land.

Merge the fix branches into the integration branch in one merge node. A conflict the merge hits is a defect in the ownership cut: fix the merge itself, then rerun the merged tree's suites. The merge node proves the union before the suites run, so a silently dropped fix branch never reaches review. Compare the pre-fix stack tip against the merged tip. Restrict the diff to the union of the fix paths; it must equal the combined fix diffs. The report carries the mismatch count, which must be 0. When the round ran more than one fix child, the merge brief pre-declares the expected value of every check it runs (suite counts, per-probe wrong counts). It takes them from the fix reports, before the runs start. The merge report prints one expected-vs-observed row per check. A single-child round skips the table and prints the check output.

Re-review the merged head as the one re-check of the fixed findings only (skill `manager`, rule T2): a fresh blind run against the same BASE. The re-review brief still enumerates the original goal findings, and the gate is those plus regressions from the fix round.
## Related pitfalls

- Sol reviewing a rebase against the old branch head sees upstream's own changes too, and can FAIL on upstream bugs. Fix those as fork patches only in code the fork builds/ships; list sibling sites in vendored, unbuilt files without editing them, and say so in the report.

- Dotfiles reviews: `hermes/.hermes/config.yaml` holds the `FLATIRON_GW_API_KEY=` line, so a diff that includes it can end in exit 3 ("user payload is not exactly the diff query"). Apply the secret-line rule of `references/verification-pass-pitfalls.md`: redact the value in temp copies and keep the diff; excluding the whole file lets the rest of it escape review.

- A child can spend its turn budget on the fix and skip the review block ("review not run: iteration budget hit"). Before Sol, check that the report contains the decision log and the reviewer verdicts. If they are missing, accept one inline review with a waiver note instead of relaunching reviewers. A report with a "reviewer's-own-verdict" caveat or "delegation was unavailable" means no fresh reviewer ran: the verdict is one self-review. Say so in the report and do not count it as the team review.

- Children's reviewer ACCEPTs are also self-reports. A subagent reruns the user-visible repro once, at the end of the last fix round (e.g. close/reopen a widget). A fix claimed as passing and accepted by the child's own reviewer can still fail.

- Fix briefs give the fix round one precondition check. Confirm the claim on the diff (`git diff <BASE> -- <file>`, does base already do the same?). Reviewers cite removed lines that were never removed, or propose a fix that is too broad. The child applies the smallest fix that is true to the facts and reports the facts it found. Probe only a finding that names runtime behaviour (a false block, a hang, an unbounded read). Run it in a scratch tree before any edit, with the current line of code quoted. The child reports each finding reproduced or 'not reproduced' with the probe output and changes nothing it could not reproduce.

- A subagent's "matches X exactly" is not evidence: compare against the real reference (e.g. the live values the UI should show). Fact-check only a claim that gates a push or a fix. Before the manager relays it, a read-only subagent checks that one fact. Use a `git rev-parse <ref>` or a `git merge-base` line against the claim. Drop every other state claim from the report. Never announce a state-changing result from the report text alone. Triage a child's findings by their own text before you relay them. A finding labelled MAJOR whose body ends in "works here" is no finding. Drop it and say so in one line. A finding that a repo "commits" a stale artifact is checked with `git ls-files <path>` and `git check-ignore -v <path>` before you relay it. A claim about how a dependency behaves gets one check before the manager accepts a change that depends on it. The same holds before the manager puts the claim into a steer or a brief. Grep the function in the dependency's source, or make one real call (`echo 'reply PONG' | <cli> run`). Don't trust `--help` text and filter its output in Python (the grep rule is in `references/dispatch-ops-pitfalls.md`).

- Diffs > 1.5 MB are refused by the reviewer script. `--repo` mode includes untracked files, so a worktree with local build dirs (`build-*/`, `.cache`, tool state) blows past the limit even for a small change. Before the first run, check `git status --porcelain` and pass `--exclude 'build-*' --exclude '<dir>/*'` for each untracked non-source path. Split per directory only when the real diff is large.
