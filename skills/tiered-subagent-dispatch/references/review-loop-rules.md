# Review loop rules (blind review depth)

Load when running or closing an adversarial review loop (step 7 of the dispatch procedure): fix rounds, contested findings, stop conditions.

## Review scope and verdicts

User rule: every adversarial review (sol and Kimi) also flags useless churn and code that can be deleted; less code is preferred. Sol's fixed prompt in `hermes-adversarial-review` (INSTRUCTIONS) and `references/kimi-review-block.md` both carry this; keep it there when editing either. Exit 0 PASS / PASS-WITH-NITS, 1 FAIL (BLOCKER/MAJOR present), 2 run error, 3 isolation breach.

An exit 3 with `no request dump found` is a tool fault, not a verdict. Run the tool once on a tiny known diff (`--repo <small worktree> --base HEAD~1`) to tell a transient fault from one tied to this diff. Retry the real review at most once more; after two discards on the same diff, stop and ask the user whether to ship on the other checks. Never relax the fail-closed isolation check to get a verdict. Known persistent cause (diagnosed 2026-10): `hermes chat` now runs each turn inside the long-running gateway daemon, so the per-request dump the script's isolation guard expects is not written where the guard looks; a diagnostic child ran the script on a tiny diff and both retries exited 3 on any diff. On that signature stop without a third retry, defer to the private HERMES_HOME tenant route of the manager skill. It counts as a real verdict. Mark the blind review waived (not passed) in the report only when that route also exits 3. Gate on the other checks until the script is adapted. **Combined (coherence) review across repos and snapshots:** the script takes one `--repo`, so build one patch and pass `--patch`. Concatenate `git -C <repo> diff -U15 <BASE> HEAD --src-prefix=a/<repo>/ --dst-prefix=b/<repo>/` per repo, plus `diff -u -U15 --label a/<name> --label b/<name> <snapshot file> <live file>` for each non-git path (skip the snapshot's `.manifest.json`). Launch the per-repo reviews and the combined one in the same background command, each writing its own result file with `echo "exit=$?"`.

## Combined (coherence) review

**Combined (coherence) review across repos and snapshots:** the script takes one `--repo`, so build one patch and pass `--patch`. Concatenate `git -C <repo> diff -U15 <BASE> HEAD --src-prefix=a/<repo>/ --dst-prefix=b/<repo>/` per repo, plus `diff -u -U15 --label a/<name> --label b/<name> <snapshot file> <live file>` for each non-git path (skip the snapshot's `.manifest.json`). Launch the per-repo reviews and the combined one in the same background command, each writing its own result file with `echo "exit=$?"`.

A finding that rests on something outside the diff (a plugin hook that replaces a removed config entry) is checked against that real mechanism; reject it with that evidence in the report, never on reading alone.

An exit 3 with "user payload is not exactly the diff query" on a diff that holds secret-shaped text (`*_API_KEY=`, `*_TOKENS=`) comes from Hermes' request-dump writer, which redacts the on-disk copy but not the wire request. The script now also accepts the query passed through the same installed redactor, and fails closed if it can't produce that copy. If it recurs, write the dumped user text and the query to files, find the first differing byte offset in Python, and fix the comparison; never weaken the one-user-message, no-tools, no-marker checks.

On FAIL: dispatch the fixes through the ladder, then review again (fresh run, same BASE). Relay the review file path and the verdict to the user. When a tool's own text output is the verdict, `sha256sum` the tool before dispatch and again at read-back: a tool that changed mid-run is a changed instrument, and the run's evidence goes with it.

- **Sol re-review gates on fix-round regressions too.** The gate is the goal findings plus regressions the fix round itself introduced (four of the manager skill's MAJORs in one round landed in text the previous round had just added). A re-review that finds only new defects inside freshly touched lines is a FAIL on introduced regressions, not fresh scope; the fix round count covers them.

**Prompt-level review outside the script.** `hermes-adversarial-review` reviews a diff. When the artifact is the prompt or skill text itself, and citations in it must be checked against a live upstream clone, sol runs as a plain oneshot job: `hermes chat --provider openai-codex -m <sol id> --reasoning high --yolo --oneshot -Q --max-turns 80 --query-file <brief>`. The user's effort cap for sol is high, never max. Tools stay on (`--yolo`) so the reviewer reruns citations against the pinned clone; the brief names the reviewed files with their sha256 and forbids writes to those files or the branch. They can write scratch files and prototypes. The blind rules still hold: the brief carries the review dimensions, never the author's intent, subagent reports or the fix history, and findings return verbatim into fix briefs, unattributed.

## No goalpost moving

**No goalpost moving (standing rule; user-directed).** The brief of every Sol re-review (and every first review that follows a fix round) enumerates the goal findings: the verbatim quotes of the findings that spawned the fix round. The verdict gates ONLY on those findings remaining unfixed or on regressions introduced by this fix round. Every other issue Sol raises (new MAJORs on untouched code, design opinions, refactors) is logged verbatim to the follow-up spec as a follow-up, not a blocker. Push/shipping decisions treat goal-fixed + new-side-findings as PASS-with-followups.

## Fix briefs name the class, not the instance

**Fix briefs from a review name the CLASS, not the instance.** Sol cites one or two files per finding; children fix exactly those and the next round finds the same bug in siblings (or in code the fix itself just added). Every fix brief says "fix this class everywhere in `git diff BASE HEAD`" and its CHECK is an enumeration: every site of the pattern with file:line and how it is now handled, plus a grep/script that returns nothing when the class is gone. If a second round finds a class the first round claimed fixed, escalate that deliverable one rung (`pick --failed`). A fix to shared parsing or classification code gets whole-family probes, in the fix brief AND in the review block: the flatiron reviewers passed a brace-list classification change on every class the test suite exercised while it regressed 16 base-correct SME2 lines no probe touched, and only the blind reviewer's compiler-accepted corpus (`clang`/`llvm-mc` output) caught it. A probe that enumerates the family from real assembler output finds that class; one that reruns only the originally reported lines does not.

## False positives need a run

**Never dismiss a finding as a false positive on reading alone.** A header declaration plus "CI passed before" is a hypothesis, not proof, and the user asks for it to be run. Dispatch a verification child in a separate detached worktree (`git worktree add $TMPDIR/<task>-wt <HEAD>`), so it runs in parallel with the author's fix round in the main repo. Its brief: build the exact path the finding names (cross-arch via the qemu user-mode emulator at each vector length CI uses), add a probe that pins the claimed type/behavior (`static_assert(std::is_same_v<decltype(...), ...>)` plus runtime asserts on edge values), confirm the arch-specific kernel is the one selected, and run one mutation to prove the probe can fail. Report the verdict to the user only from that run.

## Push gate

**Don't push while the verdict is FAIL**, even when you judge every remaining finding a false positive or a style opinion, and even when the original request ended in "then push": that covers a clean result, not a FAIL. That judgment is the user's call: report the findings with your recommendation and ask first. Then the fixes get amended in, and a fresh review runs before the one push (`--force-with-lease=<branch>:<last pushed sha>`).

## Contested findings: majority vote

**User rule: contested findings go to a majority vote.** Findings that are opinions or unverifiable from the diff (refactors, "is this abstraction needed", platform-baseline questions) are settled by three independent reviewers from different model families: the healthy Kimi, the latest Sonnet and the latest sol, launched in the same turn. Each gets one ballot brief (copy per reviewer with its own scratch dir), a read-only detached worktree at the reviewed HEAD, the findings as written, what to weigh for each one, and the findings already settled by experiment marked as excluded. Each one answers in exactly `Fn: FIX|KEEP - <evidence it checked itself>`. Fix a finding only on 2 of 3 FIX votes; report the tally per finding. Findings that an experiment can settle get the experiment, not a vote. When voters split on a FACT (e.g. "master already fails at -mcpu=power7" vs "master's ops are never instantiated there"), the vote does not settle it: a subagent runs the decisive repro on base and head (same flags, the exact type the claim names) and the manager acts on that. Before overriding a KEEP majority with a fix, a subagent also compiles the proposed fix's END STATE on that target: a guard that routes to a fallback can fail the same way through the fallback's own dependencies, and then the fix adds code and fixes nothing.

## Which findings get fixed

**User rule: fix review findings only in code the branch introduced.** Before briefing a nit (wrong comment, weak test, naming), check it with `git blame -L <a>,<b> <file>` or `git diff BASE HEAD -- <file>`: if the lines come from the branch's commits, fix them in the amend; if they are pre-existing upstream code, leave them and say so in the report.

**When the review corpus is a rebased commit stack of already-shipped patches** (not one task's fresh diff), the verdict's FAIL flag does not map onto the introduced/pre-existing split on its own. Gate on the produced tree, not on finding severities: decide whether the tree passes its checks and the review of what the rebase itself changed. Then run the intro triage of this file on every finding, marked per owning patch and provenance (pre-existing in the live patch set, or introduced by the rebase or this task). The user decides which pre-existing findings land in the same rollout, since the review is the read the tree gets; sort them by the triage into one decision list: introduced now, pre-existing A-class (ordinary use), pre-existing B or C class. Never find pre-existing defects live on the install, stay silent, and ship the update anyway.

**User rulings on findings are standing.** When the user says a class of finding doesn't matter (or picks a specific fix style for it), write it into the task's spec file as a standing rule, steer or re-brief any child already working on it, and on every later review drop that class silently instead of dispatching it. A child fix for a ruled-out class gets reverted before the next review.

**A finding that reverses an earlier round's fix** (round N asks to add a restriction, round N+2 says the restriction hides real problems) is a design trade-off, not a bug. Do not flip the line back. Brief one change that meets both findings (drop the restriction and scope the agent's fixes to the lines it changed), and name both review paths in the brief.

A child's review-round cap is enforced by the manager, not trusted to the child: count the review files it writes (`<task>-review<N>.txt`), and steer it to stop and report the moment it starts a round past the cap.

## Bound the loop

**Bound the loop.** Two kinds of stop, on different counters

Budget the loop by what the next round pays, not only by the round count. A blind reviewer scans the whole defect space of the diff, and early rounds pay for themselves: they find real defects on the common path (a diff parser that mis-reads hunk content as headers, a staged new file that loses its extent). Mechanism fixes of that class earn another round each. The loop changes character when the last confirmed findings all need an unusual setup or are already named limits with a code comment or README line: from that round on, weigh each new confirmed finding's fix against the damage the fix itself can do. A fix that guards a rare trigger can add its own edge on the common path (a shared reader that rejects a legit path, a deadline that fails open too early), so dispatch it by the class's trigger, not by the round number. A round whose confirmed findings are all "unusual setup" or "doc" and whose fixes each carry a wider blast radius than their trigger ends the loop as documented limits plus a user decision, not as one more fix round.

One design keeps failing review on new edge cases of itself (each fix exposes the next width/timer/overflow case): stop patching that design. Write one fresh spec whose design closes the classes structurally (fixed widths, decisions from the worst case, truncation at the symbol), and keep the failed design's tip on a `backup/` branch so the reversal is cheap.

The surviving design keeps failing review only because each NEW mechanism it tries draws its own MAJORs: stop after a few rounds (three was too few for the simdref auto-update restart code), close every BLOCKER, confirm or reject each new MAJOR on the code (a fresh read-only subagent, not the author's say-so), fix the confirmed ones, and hand the user the still-open findings with options instead of another silent round. A blind reviewer has the whole defect space to scan, so the manager's patience runs out long before the supply of defects does. A fix loop needs a closable end condition (named limits accepted), not "one more round". An accepted named limit becomes a one-line comment at the code site (`# shortcut: <the limit>, <when to upgrade>`); an undocumented limit re-surfaces as a new finding in the next round.

A round whose only accepted findings need an unanswered user question or an outward-facing step (push, publish, a config the router must not touch) ends the loop as pending user input, not with another round. Land the reversible fixes, report the verdict with the open items, and dispatch no further fix round until the user answers; otherwise the loop manufactures churn while its real blocker sits in the user's queue.



Before branching next steps on a verdict-shaped MAJOR, run its claim once against the real code: the JetBrains "signing credentials never reach the signer" MAJOR was wrong (`./gradlew signPlugin` with only the env vars produced a signed zip), and only a run would have caught that.

Rotate the review family when one scope reaches a third review round. Fresh sessions from one family can repeat the same blind spots. The final sol review still runs last.

One fresh FAIL with many findings of mixed machinery and prose gets one read-only triage child per run before any fix brief. The child reproduces each finding (smallest probe), classes it by impact (wrong result or paid-quota loss in ordinary use; needs an unusual setup; doc or cosmetic), and asks `which commit introduced the cited lines`. Introduction is judged against the task's original BASE or snapshot, and prior execution in an installed copy exempts nothing. Fix briefs follow the introduced-and-impactful classes first. Pre-existing or missable classes get their own fix branches inside the original final review range. Never mix them into the introduced-fix brief, so the gate's next blind run does not re-digest them.

The rerun keeps the same BASE, so a fixed pre-existing finding reappears in the next review file unless the child proves its provenance. The verdict follows the goal-findings split of this file: fixed introduced findings stay fixed; pre-existing findings that stayed on the user's list stay open; the rerun's other BLOCKER counts as FAIL. A finding with intro evidence quoted from the triage (the old patch file line) is triaged, not a new finding. A capability probe finding (a vision or web probe that guesses) gets its own design input first: the probe must use only-live input with at least two controls and treat an empty, truncated or refused answer as inconclusive, never as a stored false. A fix round can introduce the next finding (a per-item check that drops NaN, a marker move that truncates the next region), so each fix brief's CHECK must exercise the new code path, not just rerun the suite. When the same deliverable keeps failing on new edge cases of one design, stop patching: write one fresh spec whose design closes the classes structurally (fixed widths, decisions from the worst case, truncation at the edge), confirm it with the user, and send it one rung up. After the third FAIL, sort findings into introduced-by-branch vs pre-existing (visible as unchanged context in the diff). If only pre-existing or MINOR items remain, stop and ask the user whether to push or do another round instead of looping. When the user is unreachable (a timed-out clarify), the cautious default is at most ONE more round, declared to it as the last in the brief; if it still produces a real new finding, stop, push nothing, and report the findings, the measurements so far, and the options. Sol re-raises design objections every round: once only opinion or taste findings remain, or the previous round's new-severity findings were fixed and the new round surfaces a new MAJOR that is again narrow and fixable, the cost of one more round is still lower than parking the branch, but only once. Findings on edits the user made in their own original commit (scope churn, a changed default, a deleted README section; check with `git diff BASE <user's commit>`) are user intent: never brief a fix for them, bring them to the user. The same holds for the user's existing config that a job only moved into a repo as-is (permission lists, machine paths): ask once with a recommendation, record the answer as a standing ruling, and push once only ruled findings remain. Track repeat findings by file across rounds; a file that draws new findings three rounds running gets split out of the push or redesigned, not patched again. For code that validates external input (a downloaded index or manifest), the structural close is verification, not parsing: accept the input only when its size and hash match published integrity metadata (an apt Release file lists the SHA256 and byte length of Packages), then extract with a simple regex over the verified text. A hand-rolled parser accepts a new failure mode every round (truncated stanza, field order, encoding). Two paths that must agree, such as a dry-run plan and a live-run plan, share ONE planning function; the run prints or executes the same plan, never a second copy. Sol re-raises such design objections every round, so once only these plus issue-tracked items remain, ask to push without a PASS. A review verdict can rest on a path inside a CONCATENATED diff (a/REPO/... prefixes) that does not exist at any repo root (the combined review flagged publish.yml as "nested" twice, though each file sits at its repo's `.github/workflows/`). The launcher's report says whether each per-repo finding's file:line resolves in the repo itself; stray combined-diff paths get marked as diff artifacts, not shipped to fixers. A non-destructive question for the user (deletion, design choice, push gate) can time out unanswered twice while the same turn's destructive sibling is answered. Send it alone and unanswered-tolerant (state the default, proceed on timeout), and treat two unanswered sends as a decision to proceed with the reversible default, never as a verdict.

Bound the loop by the commit range too, not only by the round count. A review whose BASE sits before the user's feature commits keeps flagging the user's own design choices as findings (hook shape, memo fields, an external tool the feature calls by design), so every round fails and the fix children keep churning user intent. Widen BASE past the user's last authored commit once, as the blind-review rule already says; if the FAILs continue, stop the loop after the round that follows the widening, list the open findings as documented limits with file:line, and hand the push decision to the user.

## Related pitfalls

- Sol reviewing a rebase against the old branch head sees upstream's own changes too, and can FAIL on upstream bugs. Fix those as fork patches only in code the fork builds/ships; list sibling sites in vendored, unbuilt files without editing them, and say so in the report.

- Dotfiles reviews: `hermes/.hermes/config.yaml` holds the `FLATIRON_GW_API_KEY=` line, so a diff that includes it can end in exit 3 ("user payload is not exactly the diff query"). Apply the secret-line rule of `references/verification-pass-pitfalls.md`: redact the value in temp copies and keep the diff; excluding the whole file lets the rest of it escape review.

- A child can spend its turn budget on the fix and skip the review block ("review not run: iteration budget hit"). Before Sol, check that the report contains the decision log and the reviewer verdicts. If they're missing, launch a fresh `hermes chat` review process with only the review block plus the repro checks (never resume the author session for a review, rule 6e). A report with a "reviewer's-own-verdict" caveat or "delegation was unavailable" means no fresh reviewer ran: the verdict is one self-review. Don't count it as the team review; a subagent launches the fresh reviewers as separate `hermes chat` processes (one per deliverable, diff + checks only) before sol.

- Children's reviewer ACCEPTs are also self-reports. A subagent reruns the user-visible repro after every fix round (e.g. close/reopen a widget); a fix claimed as passing and accepted by the child's own reviewer can still fail.

- Fix briefs give each review finding a precondition check before the fix: confirm the claim on the diff (`git diff <BASE> -- <file>`, does base already do the same?). Reviewers cite removed lines that were never removed, or propose a fix that is too broad (marking every source as a new language breaks files that need the old one). The child applies the smallest fix that is true to the facts and reports the facts it found. A finding that claims runtime behaviour (a false block, a hang, an unbounded read) also gets a runtime probe in a scratch tree before any edit, with the current line of code quoted; the child reports each finding reproduced or 'not reproduced' with the probe output and changes nothing it could not reproduce. The blind reviewer sees only the diff, so claims that cannot fire are common, and a fix written to one churns or regresses the branch.

- A subagent's "matches X exactly" is not evidence: compare against the real reference (e.g. the live values the UI should show). A child's self-report can contradict itself (a pushed sha that does not match the base it claims, a "main moved back" claim on a plain fast-forward). Before the manager relays a state claim, a read-only subagent checks the one fact (a `git rev-parse <ref>` or a `git merge-base` line) against the claim. Never announce a state-changing result from the report text alone. Triage a child's findings by their own text before you relay them. A finding labelled MAJOR whose body ends in "works here" or "no action" is no finding: drop it and say so in one line. Child severity labels run high. A finding that a repo "commits" a stale artifact (export, build output, data dir) is checked with `git ls-files <path>` and `git check-ignore -v <path>` before you relay it. Children read a local, gitignored build left in the clone as tracked content, and the right report is then "regenerate your local copy", not a repo fix. The same goes for a claim about how a dependency behaves ("hermes falls back to DELETE on NFS", "opencode reads stdin", "mpm resumes into a partial download dir"), the manager's own claims included. Before the manager accepts a change that depends on it, or puts it into a steer or a brief, a subagent checks it, because a wrong claim in a steer costs a full run that fails on it: grep the function in the dependency's source, or make one real call (`echo 'reply PONG' | <cli> run`). Don't trust `--help` text, and filter its output in Python, because `grep` here is ripgrep.

- Diffs > 1.5 MB are refused by the reviewer script. `--repo` mode includes untracked files, so a worktree with local build dirs (`build-*/`, `.cache`, tool state) blows past the limit even for a small change. Before the first run, check `git status --porcelain` and pass `--exclude 'build-*' --exclude '<dir>/*'` for each untracked non-source path. Split per directory only when the real diff is large.
