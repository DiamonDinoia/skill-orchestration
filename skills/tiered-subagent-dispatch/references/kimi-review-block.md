## Review (required before handoff; GLOBAL rule)
Load the `brainstorm` and `team` skills with skill_view and follow them for this review. Do not create or edit skills or memory.
1. Brainstorm: list at least 5 ways your change could be wrong (edge cases, callers you didn't touch, state leaks, config left changed, width/colour/terminal differences, error paths). Settle each one in a decision-log row: | risk | verdict (real / not-an-issue) | evidence (one line) | fix |.
2. Team review: spawn fresh-context reviewer subagents (delegate_task) that did NOT write the code. Give each one the review-brief, the diff (`git diff` / file paths) and the deliverable checks. Each review-brief has the goal and the change from the review-brief rule in the manager skill. They run the checks themselves and return ACCEPT, PRUNE <file:line>, or REJECT <reason>. Reviewers never edit the code or the branch. They can write scratch files and prototypes.
   Every delegate_task child in this review session counts toward the spawning budget (`delegation.max_concurrent_children` when set, else the one-shot cap of 2), however brief the child is; the scheduler does not refund a finished child. Do NOT spend a child on collection or counting; do that with your own tools first. If the budget then runs out before the fresh reviewers are done, say so in the report, finish the review inline in this session, and the manager relays the waiver.
   Every reviewer also hunts for useless churn (reformatting, renames, moved or rewritten code with no behaviour change) and for code that can be deleted (dead branches, single-use helpers, redundant guards, comments that restate code). The smallest diff that passes the checks wins: each such site is a PRUNE <file:line> with what to delete.
3. Fix every real finding and PRUNE/REJECT, re-run the checks, and repeat step 2 once if anything changed.
4. A claim that a review comment is "already fixed at HEAD" is not accepted on the child's tree alone. Check it against the CURRENT upstream PR head (`gh pr view <n> --json headRefOid` and the thread state), not against the branch the child had open when it ran.
5. A child that says a test or check "cannot fail" must prove it: run it once on the change, once with the change reverted, and quote both outputs. The brief names both runs.
6. No goalpost moving. A review after a fix round enumerates its goal findings (the verbatim findings that spawned the round). Only those findings still unfixed, and regressions this fix round introduced, gate the verdict. Everything else is logged verbatim to the follow-up spec, not a blocker; goal-fixed plus new side findings is PASS-with-followups.
7. Shipped-repo check: grep the reviewed diff for machine-specific text (`$HOME`, `/home/<user>` paths, the user name, host names) in files that ship. A hardcoded home path breaks every other machine that clones the project.
Report: the decision-log table, the reviewer verdicts, and the final check results (with exit codes).
