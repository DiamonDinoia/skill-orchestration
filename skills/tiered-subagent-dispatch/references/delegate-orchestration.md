# Orchestration pitfalls for delegate_task batches

Extend this file with manager-side lessons about dispatching, watching and reporting on subagent children. Always-on dispatch rules stay in SKILL.md.

- The manager never trusts a specific value in a child report (a commit sha, a branch name, a flag string, an id) without a build source: a tool result or a file the child read. Small false details (an 8-hex sha that exists nowhere) survive into a final report, and the manager repeats them upstream. When a reported value has no such source, verify it before use and treat the child's other reported values as unverified. When the value changes a plan or gates work (a BLOCKER claim, a baseline, a pass set), read its evidence before acting: the transcript row that carries the tool output or the file the claim names. High-impact claims in the completion summary are taken from the launcher's evidence files (status, log or flags files), not from the summary text alone.

- **Unattended children and consent blocks (one rule, the home of the tool-block rule): on ANY tool block, the child never retries the command and never works around the block (no rephrasing, no encoding); it reports the block verbatim, and its other checks continue.** The report carries the exact tool, command and block message. A child that routes around the block does unapproved work and poisons every report after it (one child kept running for 3 h 40 min past its block and its partial output could not be trusted). The command the block refused also names a CLASS of commands the child must now treat as unapproved (a blocked `systemctl --user stop X` also blocks `kill`, `pkill` and any other command that stops X): the brief that touches services names the commands it may NOT run. In the child's brief, forbid every command that needs approval (`systemctl stop`, `kill`, restarts, deletes outside its own scratch) when no human answers, and give the alternative inside allowed means (a conflicting service stays up; the child serves on a free port and reports both URLs).
- The stand-in child that replaces a stalled one works from the ORIGINAL goal text plus every steer it already saw. A stall escalates one tier per SKILL.md. The salvage of the stalled child's leftover diff still applies.
- **Live fixes to a page the user is looking at go to a worktree the user is NOT looking at.** The user checks the served page while a fix or audit round runs. If a child edits the live worktree, the page changes under the user's eyes, and every check the user then does hits a moving target. The fix child works in a new worktree on a branch off the live HEAD, and the user switches over only when the round is done and checked.
- Status questions are dispatches, never a fixed sleep. When the user asks what a child is doing, or the manager needs to know before deciding, dispatch a read-only status-check child at once (intern tier does it). It reads the tail of the child's live transcript `~/.hermes/cache/delegation/live/<deleg>/task-N.log`, lists the child's scratch dir for `exit=` lines, and reports liveness from one `ps -eo pid,etime,args | command grep -E '<binary names>' | command grep -v grep` run (bracket or `-E` pattern so the pattern does not match the ps pipeline itself).
- A brief without a deadline carries the SKILL.md default of 60 minutes. Any brief for a measured sweep or multi-variant comparison names an explicit deadline sized to its run list, hours when it queues v4-under-SDE runs and a full ctest. Without it the manager has nothing to stop a slow child on.
- A background-process notice's command often ends just before the shell's trailing `exit=` line appears, so one notice can end on the run's last output while the real verdict follows in the next notice. Pass on only the phase ("it started its mutation check", "run X finished") and correct any earlier relays of the same job when the log lands; the completed-phase sentence becomes false as soon as the next notice arrives.
- When the decision is "the smallest fix that preserves the contract", prototype the smallest candidate first and add a coefficient, epsilon or grid point only where it fails. Then a positive claim ("X is the max that fixes it") exists, because an exhaustive sweep can only ever report that nothing tried above X passed. When the decision is "which of two mechanisms holds", run both arms in parallel on the same grid. Pick the ordering rule from the decision in the brief, not from the number of ideas on the table.
- A numbers-to-decision brief carries the decision it feeds, the number and unit per quantity, the comparison baseline, and a forbidden-work list (no wall-clock timing on a shared host, no extra lanes, no variants past the named ones). Children otherwise fill gaps with unasked-for variants and timings.

- **Review-model resolution for long reviews.** A routing subagent resolves the review model with `hermes-dispatch-route sync` at dispatch time when the model choice is the point. Never write the model line into the brief, so a mid-task change to the configured pick propagates without editing briefs.

- **Paid models cannot nest in Hermes.** A Hermes Opus, Sonnet or GPT leaf has no delegate tool. The `team` and parallel fan-out rules apply to flatiron-hosted models only.

- **Unattended children get no approval-gated calls.** Every unattended child brief forbids `execute_code` and every other approval-gated call: the approval prompt waits in the UI with nobody to answer it, and the child stalls to its deadline. The brief names the substitutes: `write_file` for file writes, `terminal` for code. The same reasoning covers Python run through a shell heredoc (`python3 << EOF`) or `python3 -c`: those are sent to the user for consent, and when nobody answers within 5 minutes the call dies, which cost one full vision-probe node until it switched to a script file. A brief's one Python block always goes into a file in the child's scratch dir and runs as `python3 scratch/run.py`.

## Reviews of large rebased stacks

The review brief of a whole-stack review (a rebase of many patch commits) declares the environment classes the reviewer may write off: named test-guard failures in a linked worktree, missing deps in scratch, the node_modules state. The list comes from the manager's triage, and the reviewer classes every test failure it sees as one of those classes or a NEW failure. The Kimi review runs pytest on its focus files; the brief names the classes to class its failures against, and no more.
