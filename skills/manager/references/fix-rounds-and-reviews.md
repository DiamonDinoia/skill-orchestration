Load this file when a fix round, review round or integration gate runs.

# Fix rounds, reviews and integration gates

Cut work into deliverables with disjoint file scopes. When part of a blocked node's scope has no dependency, split that part into a scoped subnode with disjoint files and CPU range, and make the original node depend on it: a blocked parent leaves free slots idle. Work meant for a PR branch commits on that PR branch. Check first (`git worktree list`, `git status --short`, `merge-base --is-ancestor <pr-branch> HEAD`). At PR head, checked out once and clean, commit directly. Otherwise build on a scratch branch at the PR head, land by fast-forward, replay other jobs' commits on top. Keep commits self-contained and path-scoped; tie each review-application commit to its reviewer comment id.

A job whose checks run tests, builds or generators gets its own `git worktree`; its brief routes every git command through `git -C <worktree>` and bans tree-moving verbs in the user's checkout (`stash`, `checkout`, `restore`, `reset`). So does every job when the repo has commit hooks or jobs commit in parallel. A text-only job may share a hook-free tree. In a shared tree, the manager takes any whole-tree rollback snapshot before dispatch, never inside a child: one child's `cp -a dir` captures a sibling's in-flight edit. Judge a shared-tree child by diffing the paths it owns; a whole-tree diff shows the siblings' writes. Commit only own paths (`git commit -- <paths>`). On index.lock, retry 5 times, then escalate; never delete the lock. Jobs sharing a resource run serially, even in separate worktrees. On a shared box, every brief names a `taskset` range and pins each build and benchmark; concurrent jobs get disjoint ranges and total threads stay under the box's cores. Pick each pin before launch: `taskset` cannot widen on a running process, so granting a live job more cores means stopping it and resuming the same agent session on the new allocation. A job still at todo takes freed cores for free: edit the core range in its not-yet-launched brief file before dispatch instead of restarting a live job or leaving the cores idle. Teach a concurrent-access rule only from a probe of the real mechanism, never from tool semantics alone. Run two live writers doing the permitted operation, a shared-tree commit or a scope split, and state what the probe proved. A rule taught from reasoning alone can hold the opposite of true and gates every later dispatch.

- Each review-brief, per-deliverable, combined-review, fix-round or Sol, gives the goal, the user's request verbatim when there is one, plus the spec row or finding. The change is the commit range, the file list and one line for each change that says what it does. The reviewer can run code and prototype solutions in scratch at its discretion, and a prototype is proof, not a commit in the inspected branch.  The brief's rules win when the two disagree.
- One combined reviewer covers the whole change set: no contradictions, one name per concept, no duplicated logic, same behaviour per condition, docs and code agree. For a change split across several branches, that reviewer also proves clean mergeability with `git merge-tree --write-tree` pairwise against the live base, chained for three or more branches; exit code plus named conflict files is the evidence, and no worktree is needed. The combined reviewer probes the corpus of wrong-result rows twice, once on the live base and once on the combined tip, and the report carries both counts grouped by defect class: counts from the base alone cannot separate shipped defects from ones the change causes. For a matcher or classifier change, the corpus covers every class the change distinguishes, drawn from realistic input of the domain (real compiler output lines, several hundred of them), not only the rows the fix briefs named: probes pinned to the instigating bugs pass every review round while an un-probed class regresses on the first realistic corpus. When an earlier trace confirmed planted content (a steer the manager never sent), the combined review also greps the whole change set for the injected tokens and expects zero hits, and maps every commit in range to a listed purpose. Findings become fix deliverables.

Encode an approved push scope as a stop rule: name the approved branch and old-tip sha, forbid other branches by name. The child runs `git ls-remote` at step 0 and stops on a different remote tip. "You can push" covers only the work it answered. The land-and-clean checklist (pre-checks, push by sha, issue auto-close, local cleanup) is `references/push-after-approval.md`. A scoped-review pass does not override the gate's blind-review FAIL.


- A loop child told to iterate until green carries pre-authorized fallbacks as trigger-to-action pairs verbatim, so it fixes the recognized failure without an escalation round. Also bound the fix surface by file scope (for example tools/ci/ only): a newly exposed failure outside the trigger list may be fixed inside that scope without a round trip, while one needing a file outside the scope escalates. The report classes every fix (infra vs ours, newly exposed vs pre-existing, workaround vs root fix) and says where each deferred root fix belongs. Bound the loop with explicit stop rules: a push count, an elapsed-hours cap, and the same first error surviving two fixes. Track the iterations in a scratch table (push sha, build number, per-leg result, first error, fix), so the final report and the next session read state from a file, not from transcript.
- A run of same-kind fix units sketches well to one senior coordinator on a quota-free binding; it spawns cheap-tier mechanism leaves and re-briefs a crashed leaf's mechanism as a fresh leaf. A leaf's completion note can stay buffered past its pushed work, so verify each unit's branch tip before queueing the next unit.
- A conflict predicted against an old base is not a conflict. Re-run the merge check against the actual new base (a stacked branch's parent tip) before writing resolution steps.
- Check the fix base against the live default branch before writing the brief. Fetch origin, then run `git merge-base --is-ancestor <sha> origin/main` on every same-topic branch's commits: merged commits are the shipped baseline, not stale duplicates, and `git diff origin/main` names the work still missing. An unmerged same-topic commit may already hold part of the fix; reuse its file blobs instead of rewriting them. A branch cut from a stale ref re-does merged work and collides on monotonic gates (changelog versions, pin shas), costing the full fix-plus-re-review round. The blind reviewer re-runs the merge-base check on the fix tip.
- Pin a squash or range check by base sha plus an empty-diff check, never by a hand-counted commit total: the manager's count and the range disagree silently until the child burns a report on a mismatch that is not a defect.
- A child's "fixed" is a claim, not a fact. A re-raised item makes the child quote the current line before classifying it. A claim that a change only reverts earlier edits of the same work line ("this patch only puts back what round 1 removed") needs two proofs before it passes review: the reverted code matches the pre-change source byte-for-byte (`git diff <pre-change-sha> HEAD -- <paths>` empty, or a sha256 pair), and a probe of the behavior the reverted code implements runs once on the pre-change source and once on the tip, with both outputs quoted. A byte match alone passes a revert that put the text back beside a call site that now drives it differently; a probe match alone passes a partial revert the diff never shows. Never relay an unverified fix claim. Check every review-cited file:line against the current diff; earlier-base reviews cite stale lines. The same holds for reported system state (a sha, a tree status, a path's reachability): a child cut off from it teaches back the expected answer, so require the observing command and spot-check the anchor against the system (`git cat-file -t <sha>`). The same holds for claims about an external toolchain's contents or versions (what a CI agent's vcvars supplies, whether a bundled compiler ships a runtime): a child without web access answers from training memory, so require a fetched doc excerpt, a live probe, or an explicit UNVERIFIED mark, and relay the mark to the user instead of upgrading the claim to fact.
- The user's standing final reviewer is Sol: before a fix's pass verdict reaches the user or a push is proposed, the last review round runs on it as a background one-shot from the manager's own terminal (`hermes chat --query-file <brief> --oneshot -Q --provider openai-codex -m gpt-6.1-sol --yolo --max-turns 80`, log to scratch). Read launch flags off `hermes chat --help` of the installed build in the launch turn, never from memory or an older log line: flags drift between builds, and an unknown flag dies at argument parse with exit=2 in the job log while the launcher's completion notice still reports exit 0, so nothing runs and the logs look healthy. Intermediate fix-review rounds ride the tier route; 'reviewed' counts to the user only once the Sol round passed. Check the log's provider and model line before relaying the verdict. A Sol round doubles as the different-model review of a third review round when Sol has not reviewed the change yet: one fresh blind round then covers both gates instead of a third tier-route round plus a Sol round. Each Sol brief pins the artifacts under review by sha256 (step 0: `sha256sum <files>` must equal a manifest the manager computed in the same turn, stop on any mismatch; for a repo review the manifest covers every tracked file, `git ls-files -z | xargs -0 sha256sum > manifest.sha256` and step 0 runs `cd <repo> && sha256sum -c --quiet <manifest>`, so any tracked drift fails the gate while ignored noise such as `__pycache__` stays out) and quotes the previous round's findings verbatim with their probe rows, with reference to the earlier briefs by path, so the reviewer checks the exact state the fix child reported. Build a round N+1 review, fix or merge brief by substituting into round N's brief file (shas, counts, the new fix commit ids with their files, probe paths) instead of writing a new one from scratch: the standing rules, probe lists, baselines and do-not-refile items carry over unchanged, and a from-scratch rewrite silently drops them. A re-review brief also orders the reviewer to re-probe every finding from its previous round with that round's own probe script saved in the previous sandbox (copy it into the new round's sandbox, change only paths, report the diff), classing each FIXED / STILL-OPEN / PARTLY with the current line or probe output quoted, so a finding the fix round silently missed cannot pass as fixed. A Sol re-review over a range the fix round rewrote (an autosquash fold, a history repair) diffs the previous round's reviewed tip against the new tip and maps every hunk to a listed finding fix; a hunk that maps to nothing is itself a finding. The tree diff replaces any sha-by-sha comparison. A Sol verdict that conflicts with an already-passed review is a disagreement, not a finding. Stop the fix loop and take the two verdicts to the user before dispatching anything; the user can waive the Sol round when the earlier pass covered the concern. An escalation over a real code dispute climbs one rung at a time, Sonnet-class triage before Opus; the most expensive model is for hard calls only.
- Calibrate the review depth to the deliverable's destination: a spike, demo branch or proof of concept the user will renegotiate with upstream maintainers gets one fresh review round and a green suite, not the multi-round fix loop. When the user says working beats perfect, `fail` the pending extra review nodes in the graph and proceed with the approved gate; a push approval does not by itself revive them.
- A review round staged on copies of live skill files drifts whenever a background fork runs skill_manage. Once per round, re-check the staged files' manifest against the live files, three-way merge each staged copy onto the current live file (snapshot as base), and rebuild the blind reviewer's baseline commit from live so the review shows only this change. Trace the writer per drifted file by its mtime plus the matching skill_manage entry in the harness log, and report the session and fork type. The promotion step re-runs the manifest check that same turn. A long job briefed on that manifest re-checks it at the end as well; a drift mid-job voids the work. Drift on a file the change does not edit (a curator-maintained skill) is a class, not a stop. Recopy the live file over the staged copy, rewrite the manifest, note the writer, and continue.
- A failure reproducing in no local lane is a configuration question, not numerics. One child first extracts the CI build invocation from workflow and logs and lists differences from a default configure.
- A CI-fix brief carries an infra stop rule: a failure inside runner provisioning, downloads or network ends the child with the verbatim error and no push, never a code change.
- Confirm the mechanism on the real test before briefing a fix. Toggle the suspected cause on the actual failing test, one variable; report both directions.
- A scheduling or concurrency check must also trip on the baseline, named in the same check, and it repeats two runs per side with the counts in the report: a race fires intermittently, so one green run on the reverted code proves nothing. A concurrency test that passes with the fix reverted is rewritten until it catches the defect, never accepted as a pass. Run race checks unpinned or on more cores than the contender count: a narrow `taskset` range serializes the contenders, the race never fires, and the reverted-defect check reads green while blind.
- Serialize, don't de-test. A queued GPU leg keeps its full test step; never convert it to CPU-only to fit the queue.
- When fix rounds keep leaving new findings in the same coordinating component, the component is the problem. The next fix brief tables the design without it. The same call exists one wave up: when several fixes of one wave each special-case the same shape (per-instruction guards, per-caller conversions), the combined review decides between patching every named instance and replacing the set with the one general rule, re-probing the evidence rows of the unit reviews before choosing; a general rule can fix several wrong-result classes with less code and no member list to keep complete. Ship the general rule only when it strictly reduces code or provably closes the whole defect class: chasing elegance into a rewrite regresses working special cases. Write the verdict as `DESIGN: A` (ship the set) or `DESIGN: B` (one general rule) with the pattern ids. A B verdict makes the rewrite its own build node, at least one tier above the fix author and never the quick model the fix wave used, and the push waits for a review of the rewritten change alone; an A verdict ships the set. A rewrite brief greps the suite for tests that reach private symbols the rewrite deletes and prescribes their expected failure mode by name (an AttributeError on a deleted helper is anticipated red, not a regression); the parallel test job re-routes those checks through the public entry point, and every failure the brief did not name escalates instead of being fixed in place.
- Before the hand-off, spend at most one narrowing round when the failing part is one heuristic: restrict it to the cases decidable from the input alone, verified against a corpus an independent oracle builds (each alias spelling and its candidate canonical form assembled with llvm-mc, kept only when the bytes match), and let every other input get no answer, because a wrong row is worse than none. The narrowing brief pre-decides the escape (drop the heuristic's commits and ship the rest, or ship it documented), so the call never waits for one more FAIL. A new parse step on user text inherits the existing parser's failure contract: an unparseable operand means no match, never an exception; the reviewer's corpus carries the encoding variants (hex letter case, very long numerals, empty operand). A fix guarded on a hand-picked list (a name set, an operand class) misses the members the original report did not name: the first review enumerates the upstream grammar's full member set and diffs it against the code's list, or each later round finds exactly one more missing member. When the defect class sits in one small decision function (a picker, a filter, a fallback chain) and per-finding rounds keep surfacing a new corner each time, the next re-review stops replaying findings and enumerates the function's full input space as a probe table: the Cartesian product of each input's states (three families in {id clean, id dead, no id} gives 27 rows), each row driven through the real entry point with expected and observed printed side by side, and a 100% match required. Reviewer-written, not author-written. A per-finding re-probe without the table only relocates the corner to the next untested state combination; the table is what ends the cycle. A test case proves coverage only when its negative run was observed on a broken version; a case whose subject cannot reach the guarded path (a mnemonic with no rows on the wrong side of the guard) passes trivially everywhere, so the fix brief names one observed-negative case per finding and the reviewer re-runs the negative instead of trusting the author's case list. A fix that rewrites an existing test (rather than extending it) keeps the old corpus beside the new sweep and gates the rewrite on mutation-catch parity: rerun every mutation the old test caught, once per ISA lane (SSE2 and AVX2 run separately; a mutation can be caught on one width and silent on the other), and require every old catch still caught. A green full-suite run proves nothing here: the rewritten test passes against the fixed code while the dropped cases stay undetected until a mutation names them.
- A re-check after a fix round covers the fixed findings and the fix diff only. The reviewer re-probes each earlier finding and quotes its output line. It hunts no new defects outside the fix diff. A fix round's reviewer runs on a different model than the fix author from the first round: the authoring model reads its own wording as natural, so the finding classes that make it through (comment phrasing, doc prose) are exactly what a second model files. A unit that reaches its third review round moves to a different reviewer model, not only a fresh session: a reviewer anchored on its own earlier verdicts of the same change waves through the defects it already accepts. Hardening one property routinely regresses an adjacent one: a fix that drops a defensive guard on an error path it does not target moves an older crash earlier, so the hunt diffs the error paths of the touched functions, not only their happy path. An atomic-write fix ended up replacing symlinked config files with regular files; an exact-match fix made the printed and the written hook command differ. The review round keeps its probe file, and the fix brief's last step reruns that probe against the fixed code, quoting each finding's line, and against a pre-fix copy saved before the edit, expecting each finding's failure rows again on the old side: a probe green on both sides proves nothing about the fix. In a chain of fix rounds, the probe's old side is every earlier fix tip, not only the base: a regression can enter at a middle link of the chain, and against the wrong old side the failure rows of a later round read as fixed when they are only re-broken differently. When the fix changes the mechanism the probe instruments (a stdin payload becomes `--data-binary @file`, two `mktemp` files become one `mktemp -d` directory), the reviewer's probe no longer runs on the fixed code: the fix child copies the probe, adapts only the instrumentation site, lists every adaptation in its report, and keeps the reviewer's probe byte-identical for the pre-fix run. The re-review adapts from the newest probe copy, never from the original. A reviewer probe that asserts the old buggy invariant dies at its own assert on the fixed side, before it prints post-fix values; keep the pre-fix run byte-identical and get the fixed-side numbers by running the probe under `python3 -O` (asserts stripped) or through a thin wrapper that prints the raw output. Name the workaround in the report, so a false-looking line (a one-level scan printing `retained=false` when the payload moved one level deeper) is not read as evidence the fix failed. A fix that re-routes an existing test helper's view (a locator that now looks one level deeper) re-maps every existing assertion through the new view silently: the re-review re-verifies each changed assertion still tests its original intent, not the view edit itself. The re-reviewer drives the real entry points (the shipped functions, the live server), never a simulation of the old failure: a simulated probe replays the buggy sequence by hand and fails against fixed code too, and a fix can pass a simulation while the real path stays broken.
- When an experiment can run beside CI, push the confirmed head first. Dispatch review and a CI watcher on the pushed sha. Run the experiment in a third worktree on that sha.
- A coverage gap in correctness code ships as an asserted test at its seam, not a documented note.
- A coverage gap behind private state gets a reachability verdict plus a fix proposal. The manager decides on widening the header. Never pair the verdict with an order to fix.
- A passing check does not retire a defect. A cell passing on one lane or thread count can still miss on another. Report pass and miss lanes separately; never close a defect on one green lane.
- Green branch CI proves only the workflows that fired. When CI is a landing gate, read the workflow's `on:` triggers: a matrix that fires only on the default branch never ran on the feature branch, so its cells need local legs in the gate or the push accepts a red window on the default branch.
- No keep/revert call before the regression evidence exists.
- A blind reviewer gets a commit range starting after the user's own unpushed commits, plus an explicit file list. Never a whole-file snapshot diff. Check the run before the verdict: the request dump must name the change's files and any SKILL.md files. A 'No SKILL.md files detected' dump means a broken prompt and voids a PASS. A one-shot review profile cannot skill_view, so a prompt that relies on it is broken on arrival. An exit 3 'no request dump found' with a flagless `hermes gateway run` daemon up is an artefact; rerun once. Triage findings by their task-range commit. A user-owned review script is pinned by sha256 and re-checked before each round; the report names the reviewer model. Generated and committed-data paths (lock files, eval results, big fixtures) are excluded with explicit patterns so findings stay on the change. Every review greps the diff for machine-specific text (/home/ scratch paths, host names) outside commit metadata and expects zero hits; a scratch path in a shipped comment or test string hides until it rots. A vendored-upstream sync (a version-header bump, a resync of vendored code) reviews the whole upstream release, not only the ported file: the reviewer diffs the vendored file at both upstream versions and gives a port-or-skip verdict on every other change the release carries; a bump touching only the synced file can miss a neighbouring patch or config change shipped alongside it.
- One fix brief per repo carries the design for the finding's whole class, not only the cited line. Inside that brief, the class fix opens with a complete site enumeration: grep every expression of the class in the named files, write each with its protection state (clamped, guarded, untouched) to an audit file, then fix every unsafe site, not only the one the reviewer's probe fired on. For a path-access guard the fix shape is resolve-once-at-entry: the check and every later write use the same resolved path, because a guard that resolves for the check but writes by the unresolved path still passes its own probe while a symlink bypasses it. The same shape holds for output that crashes on unusual input: enumerate every site that formats the value (every print, stderr and error message in a CLI, via `print(` and `sys.stderr`), because escaping the one site the probe fired on leaves its dozen siblings crashing. A Python CLI that prints filesystem paths dies with UnicodeEncodeError on the first raw non-UTF-8 name, after the work behind the line already ran and before any restore hint prints; the fix shape is one shared output configuration (`sys.stdout.reconfigure` and `sys.stderr.reconfigure` with `errors='surrogateescape'` at startup, so raw bytes print back as the same bytes, and `shlex.quote` on any printed command line the user re-runs, so the line round-trips the path when fired in a shell). Prove it with cases built from raw-byte names (`os.fsencode`, e.g. a name like `b'caf\xe9'`) observed failing on the pre-fix copy, plus one suite run each under `PYTHONIOENCODING=ascii` and `LC_ALL=C`: the reconfigure must win over the environment's error handler, which is exactly what those two runs test. A fix that covers hand-picked sites leaves one unfixed sibling for the next round to find, whatever else it proves. Triage the finding read-only; write the rule; fix every place it applies in the repo. A review round with several findings gets one read-only triage child before any fix brief: it reproduces each finding with a probe in scratch and classes each by impact (wrong result or hang in ordinary use; needs an unusual setup; eval-only or cosmetic). Fix briefs cover the first two classes and any parity break in the third; the rest ship as `shortcut:` comments at the code site naming the upgrade condition, plus a documented limit with file:line. A claimed race gets a forced-interleaving probe against the real entry points, with serial-order controls on both sides of the window. Force the window with calls, not sleeps: a second connection executes one side's write between the first side's read and write, which is deterministic where racing timers is not. Timeout paths run on a tiny timeout or a fake clock, not wall-clock waits. The probe prints expected and observed for each case and names which side reads whose data. The settle of the race is one conditional write with a re-read on zero rows changed (0 rows = the other side won, so return its value), never last-write-wins: two unconditional writes let both the answer and the timeout report success while the asker sees only one. A poller that re-reads its row by a resettable key matches the row's full identity (sender, body, creation time), not the key alone: a store reset that recycles ids lets the waiter adopt another client's row and return that row's data.
- A reviewer that overlapped the job's dispatch context is not independent. Its PASS counts as no review.
- A mutation leaving every shipped test green means nothing pins the change. Class each silent-pass mutation before acting: one leaving every output bit-identical (both sides of its moved threshold agree to the last bit) is an accepted coverage gap for the do-not-refile list, because no test has a wrong answer to see; one changing behaviour the suite never exercises (a clamp no test constructs below, a fallback no case drives) gets a pinning test plus a rerun of the mutation as proof. Pin a clamp by constructing below the floor and requiring bit-equality with the floor value. A test that pins an internal allocation-size choice by measuring external free-memory deltas depends on the pool allocator's chunk granularity: a wrong size inside the same chunk class reads identical deltas, and a naive small-delta probe reads zero. Prefer an assertion on an output the suite already trusts (a method comparison, a direct sum at one placed point); when no public readout can fail on revert, ship the gap as `UNRUN: <mechanism>` in the test commit instead of a memory differential that only one pool configuration honours.
- A second fix round on the same finding reuses the first round's worktree and depends on it in the graph; the brief's step 0 pins the new tip (`git -C <wt> rev-parse HEAD`) and probes `status --short`, naming any known leftover path (a seeded home skeleton a round-1 test run wrote with cwd inside the worktree) as allowed noise so the child does not stop on its own files. The pin is re-read at dispatch time, never copied from the round-1 report.
- An exit 3 'no request dump found' on an isolation-checked review is not an artefact to retry. The artefact sentence above covers only a review with no isolation check. Rerun once, then fix the routing. A review script that sets its request-dump env var only on its `hermes chat` child never gets a dump when a shared gateway daemon is up, because the safe-mode chat attaches to that daemon and the request is built in a process that lacks the variable. The child env cannot travel over the attach; an identically retried run exits 3 every time. The working route is a private tenant home: run the review with its own `HERMES_HOME` outside the shared one, so the chat starts its own gateway daemon that inherits the dump variable where the request is built. The shared user daemon must never be stopped, reconfigured or signalled; confirm it is still alive after the run and stop the private daemon (if one remains) only by its own PID proved from its environ and its home's pidfile. A private home breaks the script's model resolver, so pin the reviewer model explicitly through the script's override variable. A review counts only when the script itself exits 0 or 1 after its own dump check, never when the log merely looks healthy.
- A coverage gap noticed while a fix is in flight belongs to the node that already owns that file: steer the live child with the new case added to its existing brief, or queue a follow-up node that depends on it. The one-writer rule of the dispatch graph applies: never dispatch a second writer of the same path in parallel.
- A fix that changes which inputs are accepted names the fallback direction for every refused input row in the brief (which side the code falls back to, e.g. the profile endpoint, never just "never produce a refused resume"). The manager pre-commits the accepted fallback; the child does not pick it under time pressure, and the round-2 reviewer tests exactly the row that flipped class between rounds.
- A user's "go push" covers the push step only. The review gate the push stack holds re-runs against the post-fix tip before any second push, and a review FAIL stays a failed graph node whose dependents stay blocked; approval of the push does not leapfrog the gate. "Fix the defects" after a FAIL authorizes the fix round, not the push: the re-review still gates the stack, and a second FAIL blocks push again even after the fix nodes turn green.
- Before any fix brief, one triage runs. Fold it into the fix brief as per-finding confirm steps on a small FAIL. Dispatch a separate read-only triage child only on the two trigger shapes below.
- An evidence-free review FAIL is the first trigger shape, not fix material: a FAIL whose report quotes no output line for a finding, files an unexplained status (an opaque FOREIGN), or counts that cannot coexist with its own findings (0/0/0 wrong on base, old and tip beside a claimed wrong line) contradicts itself. The triage runs by a model that neither wrote nor reviewed the change. It reproduces each claim against the exact tips the reviewer names (base, old stack, tip) with the decisive line quoted per side and each claim classed TRUE or FALSE; it also checks the broken-probe classes first (the reviewer's script importing the wrong tree, the wrong entry-point variant). A claim that proves FALSE discredits the report's unverified claims too, and the re-review reruns on a different model, not on a fix.
- A review FAIL on a patch stack with more than a couple of major findings is the second trigger shape. It is a review-pass defect until triage proves otherwise. The triage reproduces each finding against the live tree and classes it by whether the last fix round introduced it (diff the owning patch file between its two dotfiles shas), whether the user's own setup hits it, and by impact. Fix briefs cover what the last round introduced and what ordinary use hits; the rest is a documented limit. Several of a large fix round's majors can trace to the standing code, not the round, and a blind reviewer that re-files a KNOWN class as NEW burns a round. On a stacked-change review (a rebase, a port), the triage reproduces each finding on the pre-session base of the stack as well as the tip, so INTRODUCED and PRE-EXISTING findings split before any fix brief exists. The triage brief also lists which toolchains the host actually has (cross compilers, emulators, optional SDKs), so each fix brief states up front what it can test locally and what ships `UNRUN` until CI. When the triage's answers are "the last round introduced nothing" and "the user's setup hits none of the guarded paths", the question is keep-shrink-or-drop, not which fix goes first: the triage brief names the options (drop the change, shrink it to the paths the user's setup reaches, or fix the findings and keep it whole), and the manager takes the pick to the user with a recommendation. Fixing dead-path findings to green spends a review round on code no caller drives.
- On a small FAIL (a handful of findings, each a named line with a plausible text fix) fold the triage into the fix brief as a per-finding confirm step instead of a separate triage child. In every fix round, a reviewer's proposed replacement text is a claim, not a fix: the fix brief orders the child to confirm each proposal against the code or a probe before applying it, and on disagreement to quote what the code does and report the proposal as wrong. Pasted unconfirmed, a confidently phrased false proposal lands a new wrong fact in the exact spot the reviewer named.
- A fix round on N findings runs N worktrees in parallel as far as the graph allows, one per finding, each with its own union proof at its tip, and each carrying the mutation check of its own finding: one child running several fixes and then their mutation checks serially costs the round the sum of all fixes instead of the slowest one. The rule holds for scratch copies with no git: findings that share one file split by file ownership (code plus its tests, docs plus other tests) or by `path#symbol` scopes; a shared file alone never serializes. The merge consumes the fixups by folding each into its patch commit and proves plain-to-merged equals the concatenated fixup diffs with mismatch count 0 before the live swap. Each fix lands as a `fixup! <deliverable subject>` commit so `git rebase -i --autosquash` folds it into its deliverable commit without a hand-written todo list.
- A branch assembled from disjoint-file work branches is green only at its tip by construction: a registration commit can precede the file it registers (ctest config fails at the older commits), and a repair commit can land several commits after the stub it fixes (those commits do not compile). Gate the integration per-commit: each commit configures and builds its touched targets in a detached worktree, and the combined reviewer reports a cfg/build row per commit. Repair non-building history by reordering (register after the file exists) or by folding the repair into the commit that broke it; the repair run keeps every `Assisted-by:` trailer of the folded commits, takes a backup ref before any `reset --hard` of the integration branch, and ends with an empty-diff check of the new tip against the reviewed tip plus a full-suite run at the new tip.
- The fix-round fold and integration-gate mechanics live in `references/fixup-fold-gate.md`: `fixup!` targeting, blame-based hunk splits across commits, backup-ref recovery on fold conflicts, the disjointness proof, the per-commit build gate, and the merge-readiness check.
- A cosmetic-only class kept as-is across rounds gets a `KNOWN-COSMETIC` tag in the re-review brief, naming the triage file that recorded it, so the reviewer does not re-file it as NEW. The same holds for every accepted documented limit, dependency assumption and environment cap from earlier rounds: the re-review brief carries a do-not-refile list with one line per item, or the fresh reviewer spends findings on already-decided gaps.
- Send each blind review of a pushed feature branch while the integration child still runs, and fold its findings into that child by `steer`. A review that arrives at final-report time restarts the gates and costs another cycle.
- An artifact built from partial reruns or from a run that logged a failed write is provisional. One spot-check row in the consumer's report reruns a generating step and compares one number before a dependent node consumes the artifact.
