# Fix-round fold and integration gate

Mechanics of the merge after a fix round and the gate that proves it.

- A fix for wrong text (a comment phrase, a doc wording) gets the same class sweep as code: grep every instance of the phrase across tree and docs before the fix brief, since a second instance outside the folded commit survives the round, and an instance whose owning commit sits below the rebase base can never fold. Text that went stale because a commit changed the fact it cites folds into that commit (locate it with `git log -S '<changed fact>'` or `--grep` on its subject), not into the commit that wrote the text. A `--fixup` target is a sha every earlier fold rewrote, so the brief resolves it at apply time (`C=$(git -C WT log -1 --format=%H --grep='<subject>')`, then `git -C WT commit --fixup="$C"`), never from a copied sha. A `fixup!` subject names the topical commit, but the fold conflicts when a later commit in the stack rewrote the lines the fixup changes: the context does not exist at the target. Before the merge, blame the pre-fold tip for every line a fixup hunk touches and target each hunk at the newest commit the blame names on its context or removed lines; a fixup whose hunks blame to several commits splits into one patch file per target, each applied and committed as its own `fixup! <that subject>`. A content conflict in the fold is a targeting error, not something to hand-resolve: the child takes a backup ref, `reset --hard` to the pre-conflict tip in the scratch worktree, retargets, replays the remaining fixups, and requires `git diff <backup> HEAD` empty before the fold reruns. The post-fold tip check is content-only: zero `rg` hits of the phrase plus `git diff <pre-fold-tip> HEAD` showing just the intended lines, because every sha above the base changed. Two fixups that share a subject stem ("Add GitHub Actions CI" twice) fold both children into the first match; check the fold with `git log --format=%B` against the authored subjects before the push. When the fold or a stack repair rewrote any commit sha, the final blind review diffs the pre-fold backup tip against the new tip as a tree diff (`git diff <backup> <new-tip>`); a commit range over rewritten history names commits that no longer hold the reviewed text.
- Build each commit in a from-scratch build directory: a reused directory's cached artifacts (a stale shared library from an earlier commit) can mask an ABI or build break the commit introduces, so the gate row reads green on code that does not build. When an external toolchain caches the absolute library path it discovered from a build-directory glob (a Julia binding precompile resolving `build*/lib<name>_c.so`), per-commit directory names go stale mid-gate and later commits load a deleted path: keep one stable build path per tree and empty it before each commit's configure instead. A commit that breaks by design (an API-change commit that legacy callers still compile against) is named in the integration brief with its expected failure and the node whose later commit repairs it; the gate reports those rows as expected, not as defects, and any other failure is a stop.
  Before merging N disjoint-file branches, prove disjointness by diffing each pair's `git diff --name-only <base> <branch>` sets; the merged stat must equal the union, and the merged tree must reproduce every source branch byte-identically over its own file set: `git diff <branch> HEAD -- $(git diff --name-only <base> <branch>)` empty, one run per branch with the literal branch names. When fixup commits stack on the source branches, fold each into its deliverable commit in the merged worktree with `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <base>`; the fold can hit comment-only conflicts from fixup reordering, which resolve to the source branch's reviewed text, after which an empty tree diff against the pre-rebase tip (ORIG_HEAD or the backup ref) proves the fold changed no content. The folded stack carries the same per-family identity checks, plus `git log --format=%B` showing no `fixup!` subjects. A fix delivered as a patch file whose hunks touch a file a sibling fix also edits gets a merge-readiness check the same turn it lands: `git worktree add --detach` at the sibling tip, `git apply --check` there (with `--3way` as the fallback that names the conflicting hunks), then remove the temporary worktree. An apply failure orders the two fixes by hand before the merge, never after a broken integration.

- A fixup target comes from the fix branch's changed paths, never from the commit the finding text pointed at. The reviewer attributed the finding by subject, not by blame. The brief resolves each target with `git log --format=%H <base>..<tip> -- <paths>` on the stack. A fold that aborts twice on targeting stops and re-derives every target from the file sets. Resuming with the same targets replays the same conflict.

## When a review loop refuses to close

- When successive review rounds each find a fresh instance of one guard's uncovered case (a per-file table, a timestamp-based change detector), the next fix brief replaces the guard with a mechanism that covers the class: back up the whole config root into a reserved sibling dir, `diff -r` it against the live root after each command, and resolve harness config roots from the harness's own env vars (`${CLAUDE_CONFIG_DIR:-$HOME/.claude}`, `${CODEX_HOME:-$HOME/.codex}`) rather than a hardcoded `$HOME` path. A case-by-case patch hands every later reviewer the same finding class with a new instance, and the rounds never close. Widen by replacement, not by growing the table.
- A FAIL on a round the manager announced as final is a user decision, not an automatic next fix round: present ship-with-known-limits, cut-the-feature, or one-more-round, with a recommendation and nothing dispatched yet. When one feature produces every round's findings (a config-mutating install path), the cut option the user hears is that feature reduced to its non-mutating variant (skill links instead of native plugin registration), which deletes the finding class instead of out-probing it. Auto-starting a round past a stated cap buries a scope question only the user can answer.
