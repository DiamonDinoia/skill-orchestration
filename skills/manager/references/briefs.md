# Brief rules

## Dispatch briefs

A user formula or rule arrives in the brief verbatim, with the manager's reading and each ambiguity kept as a candidate. A solution shape the manager rejects (ruled out earlier by measurement or round) is written into the brief up front. A broad decision mandate (do what you think best; accept anything) still expires at the next user message: new work declared after the mandate rides over old fix rounds, and the brief fixes CI-relevant decisions (commits on the integration branch, no publish step). Ask the user only for an open outward-facing step.

- Quote shell commands in a brief in the form that runs under the child's shell. An alias can change flag parsing, so a briefed `grep -E <pat>` can die on the flag parse. Use the syntax the child's shell resolves, or give an absolute binary path. Pin the same flag style for every command a child is told to run.
- An edit to a JSON config (live or dotfiles-managed) goes raw-text: the brief orders an anchored find-and-replace that touches only the named block and bans parse-and-dump round trips (`json.load` into memory, `json.dump` back). The default serializer escapes non-ASCII as uXXXX sequences and rewrites formatting, so a one-block fix lands as a whole-file rewrite that fails the minimal-diff review and hides noise among the churn. Symlinked targets get realpath'd first and backed up as a copy of the real file; the verify pair is `python3 -m json.tool` exit 0 plus a diff against the backup whose only hunks are the intended block. The same raw-text route serves YAML: anchored line edits against line numbers (one sed per line, never parse-and-dump), `yaml.safe_load` exit 0, and a diff limited to the touched value lines. Before editing any config value, grep the key name over the user's scripts, cron entries and user timers to find automated writers: a key an automated sync manages needs the sync's source table changed in the same round, or the sync's next run writes back the old value and the edit silently reverts. The verify diff can also hold lines nobody dispatched: the live harness persists runtime flags into its own config file asynchronously (onboarding-seen markers on session start, seconds after an unrelated edit). Match an unexpected line by file mtime and a grep of the key in the harness source before blaming the edit job, and never fold it into a revert.

A step that builds on code another step prepares risks testing the pre-edit copy. The brief orders prepare steps before edit steps per check, or adds a `cmp <prepared-copy> <worktree>` guard before each numbered run plus a repair step: copy the final files and rerun. A log directory whose older files a step overwrites hides those runs; the brief reserves each log file per run.

- A step feeding a data-loss or security acceptance rule gets its mutation check in the same brief item. Show the check fails when the change is reverted.
- Mark the closing live-proof step of a deploy brief as mandatory in the step text. On deadline pressure a child skips a numbered step it reads as optional, and nothing in the report enumerates skipped steps; the deploy then ships on code-plus-local parity while the live behaviour stays unproven. The gap closes with a fresh read-only verification leaf, never a resume of the deploy child.
- A brief that reruns an existing suite prescribes the baseline counts at the start sha (passed, skipped); the report's counts must equal the baseline plus the added cases, so a suite that silently drops cases nowhere reads as green.
- A gate that reruns part of an existing suite on an edited tree runs the same part on the unedited tree at the same revision and compares the two failure sets: a gate green only on the edited side proves nothing. A base move mid-task (a rebase onto a freshly fetched upstream) is a second edit nobody dispatched: rerun the same suite part on the pre-move tip and diff the failure and skip sets test by test, because an unexplained count jump after the move belongs to the base, and shipping it unexplained buries a corpus change the fix never made. The unedited run must start in the same dispatch as the edited run (rebuild time hides the missing baseline otherwise), on a disjoint `taskset` range in its own detached worktree (`git worktree add --detach`) from the base sha. Its brief forbids `cd` into the user's checkout. On a test runner whose per-test timeout plugin lives in untracked user config (pytest-timeout in `addopts`), add `--timeout` to the briefed command or the run has no per-test cap: brief the two runs as one command per side with identical flags, on pain of a child reporting only the edited side.
- An end-to-end test of a new gate lets no other fixture element do the gate's work. A deleted file that moves the ratio, or a pre-existing blocker that fires first, hides a gate that never opens on its own. The same holds for a test that an agent follows a recipe, tool or section from a skill: the test agent's brief must not name the mechanism (the tool, the CLI, the section title), or the test measures the brief, not the skill. Judge the agent from its recorded tool calls in the harness session store (session id from its run log, messages read with the python3 sqlite3 module, read-only), never from its prose summary: score each was-it-used question with the quoted command. Fix the ground truth independently of any component under test (a hand-written table from an independent tool before the agent runs), so a shared misreading cannot pass both sides.
- A long background run (a sweep, a refit grid, a build battery, a two-arm suite gate) launches from the manager's own `terminal(background=true, notify=true)`, never as a background job inside a child: the harness reaps the child's surviving processes when the child returns. A brief that says "launch X in the background and report" reads to a cheap-tier child as permission to queue the runs and exit; the runs die mid-flight and the follow-up step never runs. Keep every long job on the manager's slot. The child writes the probe and the exact launch line; the manager fires it and keeps the notify slot. A child may launch its own background job only when it also waits for that job's exit inside the same turn (a process_manage wait loop), so nothing survives the child; this is how a second long job runs beside the manager-owned one. A job that must outlive its child still launches from the manager's terminal slot.
- A doc or comment states the rule behind a live-computed value, never the value itself. The current rank, quota or probe result belongs only in the live table; a docstring quoting the last run's value reads as the spec to the next reviewer and rots on the next change. A doc-text fix that claims tool behaviour (a known-limit sentence, a count in a message) needs the same proof as a code fix. Probe the behaviour on the real tool before the sentence ships. A claim that spreads one property across an enumeration ('tools A, B and C return field F') gets one probe or schema read per member, never one probe for all: the author writes the sentence from the first site it read and copies the property to members whose contract differs, so sampling one member passes while the rest ship false. A line written from code reading alone can be as false as the claim it replaces.
- A brief that dictates deliverable text verbatim (changelog bullets, commit subjects, doc lines) has two failure shapes. The child can paste the brief's own instruction phrase into the deliverable (the imperative behind the draft lands in the changelog line), so the check greps the produced text for the brief's imperative sentences. And a verbatim mandate collides with any lint gate the same brief imposes (a ste.py lint against dictated wording): pre-authorize the lint findings the dictated phrases produce, or the child stops on copy-exact versus lint-clean with no resolution and burns a round.
- A brief for a release commit reads the repo's release section (CONTRIBUTING.md, the workflow file) and quotes the step line it applies: the child that is also told to version-bump can double the bump the CI workflow already commits, or leave a lock file one version behind. Who bumps the version (the brief child or a workflow) is decided in the brief, with the quoted line as evidence.
- Anchor discovery to a rule, not to remembered names. Give the command set that produces the list (`gh pr list` over the period, `git log -S <symbol>`, `git branch -a`, `gh pr list --search`, label filters). Then hang the confirmation check on the user's description (plot count, author, file). Known instances are examples to confirm, never scope. Skipping the rule part finds only the instances already named.
- A URL, hash or entry key a child must open arrives byte-for-byte from the user's message pasted into the brief, and the brief tells the child to paste it from the brief into probe scripts, never to retype it. One drifted character in a probe URL turns a passing system into a reported defect, and the diagnosis round then chases the drift instead of the site. A probe failing on exactly one input while sibling inputs pass suspects its own input first: check the key exists at the data source before blaming the code, and report a bad key back as a probe error, not a site defect.
- A brief pins an expected HEAD by its full sha, never by a short sha: two branches can share a prefix, and a match check then passes on the wrong branch's tip.
- Quotes in a research brief arrive verbatim, with author, source number and URL.
- A brief for work in a tree names where outputs live, forbids other paths, and names the scratch home of throwaway scripts. Make cleanup or an empty `git status` a listed check.
- A brief for a restricted-filesystem harness names a scratch dir inside its workspace roots. Every check that needs a write outside it is marked `UNRUN` with the reason.
- A brief that fixes derived values (constants, pixel bounds, table numbers, sizes) names every target in one line and the source of truth each derives from, never a numbered list of the values to write: an enumerated list invites the child to hard-code the listed values and recompute nothing, so a neighbor the first pass got right regresses on the next derivation change. The brief orders the arithmetic copied from a nearby instance the first pass already computes correctly (a sibling kernel's bound loop, the adjacent row's formula), and the check recomputes every target from the source of truth rather than diffing against the listed values.
- When the user's own follow-up message widens or narrows a running child's scope, `steer` the live child; a second child covers only work the widened scope still excludes. (For a steer the manager did not send, the anomaly trace rule above applies.)

A clarifying-question form that times out (outcome `timed_out`, every entry unanswered) means the user has the default interpretation. Proceed with the recommended first option on each question you already wrote, and state them in the next report. A choice taken from a timed-out form is provisional. At most one follow-on round may use it. Re-ask it at the next user contact before any release step. Flag every irreversible step (push, publish, outward-facing) as still gated on explicit approval. The manager decides; the user is not a status line.

Placeholder-shaped tokens anywhere in a goal read as unexpanded template markers and the dispatch is rejected: angle-bracket text (`<first error line>`, `<repo path>`) and `${VAR}`-style shell-interpolation text (`${BASE_URL}/chunk.json`), also inside a backticked command fragment in prose, and also inside the report-format spec line (`Report: X: UP <id>`). One offending task rejects the whole batch pre-dispatch, so every sibling task must be resubmitted too. Write the literal value (the path, or the string the child prints), in quotes; when there is no literal value to give (a scratch path the child creates, a constant the code defines), name the mechanism in prose, such as pytest's tmp_path or `SIMDREF_BASE_URL + '/detail-chunks/'`. An example payload inside a command (the JSON stdin of a hook script, where one field would hold file contents) is the same shape: the child builds the payload with an inline python that reads the file, never a bracket placeholder. For a value the child resolves in an earlier step of its own brief (a resolved model id, the readlink result of a symlinked file), have the child assign it to a shell variable inside its own command line (`R=$(readlink -f ...)` then `"$R"`, `M=$(...)` then `-m "$M"`) and write the later steps against the variable; a bracket placeholder in a later step fails validation even though every surrounding command is final.

- Skipped checks name their reason: `UNRUN: <reason>` on the outcome line. A skip without a reason reads as a pass. A disclosed skip goes to the documented-limits list of the report. It never starts a round on its own.
- A user input that arrives as completions of dispatched question jobs (install diagnostics trailing a README line with no repo issue yet, wrong-result asm lines quoted in chat) converts straight into fix and doc graph nodes. It has no ticket id, so the unanchored-discovery rule applies twice as hard: enumerate targets by rule (the README's own sections, the repo's issues), never by the one line the user quoted.
- A child may change behaviour beyond its brief only flagged: the report separates briefed work from the extra change, names its cost and blast radius, and the manager records the adopt-or-revert call and relays it to the user. An unflagged extra change is itself a finding.
- A size bound in a brief (diff lines, touched files) is a proxy for a property, never the property itself. When a child exceeds the bound but machine-proves the property (bit-identity diff of 0 on a large corpus), the manager accepts without an escalation round and says in the report why the bound lost to the proof. Escalate only when the property itself failed or went unproven.
- A fix brief that removes a step also names the lines that exist only to serve that step. A child told to remove the step and keep everything else keeps the orphaned helpers (its announcing echo, its sleep, its log print), and the next review finds them as leftovers.
- A docs restore or rewrite brief names the author-qualified base commit (`git log --format='%an'`, not only the newest matching content), keeps a user-authored notice or section byte-identical (the reviewer diffs it against the base), and requires every surviving code snippet to be extracted, compiled and run. The review greps every dependency or capability claim against the build files: a stale claim is the common must-fix.
- A draft written for the user obeys the child report length rules. The brief states the line cap.
- When the user names squash-on-land, the brief drops intermediate commit hygiene and gates only the squashed tip.
- A squash-on-land brief carries the exact reset and push command as a checked step. Its check is an empty-diff proof against the reviewed tip.

## Node brief shapes

- For the patches of one series: land patches 1..N-1 in one child and run patch N's suite gate as its own node. In one child the gate runs only after the full series landed, so a hunk the gate cannot catch ships inside the passing N-1; per-patch gates or an explicit per-hunk review are what catch it.
- Producer and consumer start together when both briefs fix the data shape. The consumer tests on a fixture. A consumer that must also accept older producers treats the shape's absence as the old behaviour, byte-compared against the pre-change consumer, so either side ships first. The assembly node that merges several disjoint-file branches carries its expected seam in the brief: the ordered cherry-pick list of full shas, conflict = stop, and the one bounded adapter edit it may make where the fixture-built consumer meets the real producer (named files, [ESCALATE-TO-MANAGER] beyond, at any numerics or public-API change). Without the stated bound the integrator either redesigns silently or stalls on the expected mismatch. A consumer whose tests pin the producer's not-yet-built output strings derives every expected string from a probed ground row (the corpus line run through the existing engine), never from reading a data table by eye. A foreign architecture's form name reads as garble to a model and gets misclassified. The brief separates the pin into a safe negative core ("no x86 form on this line") and positive name assertions backed by their probe rows, and pre-authorizes the mismatch rule: a probed row beats a read expectation, both sides report a mismatch as an expectation bug first. A consumer living in a second repo that pins the producer by a FetchContent tag or commit hash commits its API update against the old pin and builds against the local review branch through `FETCHCONTENT_SOURCE_DIR_<NAME>` on the configure line, so no machine path enters the commit; the pin bump to the new sha is a named open item gated on the producer's push. Verify base and edited side by side as two detached worktrees of the consumer, building and testing both and diffing numeric output: a drift between them traces to the producer's landed commits between the pins, and only the side-by-side run separates that from a defect the update introduced.
